The harness, and software you can reshape

An agent is a loop, a tool protocol and a prompt, wrapped in whatever isolation you actually built. This page takes the DeepSeek harness running in this fleet apart, and then hands you the controls: a simulated run you can re-price by changing one setting at a time, and a plugin explorer where you can add a hook, deactivate a tool and fork a session.

This page calls nothing. The playground and the plugin explorer below are deterministic simulations: no key, no network, no model, no extension loaded. Every number they show is computed from the controls and a scripted transcript. The playground section and the explorer section each say exactly which mechanics they do and do not model.

What the harness actually is here

The harness is @earendil-works/pi-coding-agent, with pi-agent-core and pi-ai underneath it. It is a Node process that owns four things: the loop that decides when to call the model again, the tool registry that turns the model's requests into local processes, the transcript that is re-sent on every request, and the prompt assembly that decides what the model is told.

In this fleet it runs headless, under systemd, with no terminal attached. Its parent process is remote/lane-host.mjs, which speaks to it over JSON lines over a pipe: one JSON object per line in, one per line out. The model itself is a remote HTTP endpoint (DeepSeek, reached through the exe.dev HTTPS proxy). Everything else on this page — the loop, the tools, the transcript, the compaction, the prompts — is local code you can read, restart and change.

That split is the whole point. Swapping the model is a configuration change. Swapping the loop is a code change. The interesting engineering is all in the second category, and most writing about agents collapses the two.

The loop, in plain language

  1. Build a prompt: the base instructions, the lane's role text, the project's context files, the task, the transcript so far, and the JSON Schema of every tool this run may use.
  2. POST it to the provider. The reply is text, tool calls, or both.
  3. If there are tool calls: validate each argument object against its TypeBox schema, run the tools locally under your operating-system permissions, append the results to the transcript.
  4. If the assistant made any tool call, go back to step 1. If it made none, the run is over.

One turn is one assistant response plus the tool calls it carried plus their results — appended, not replaced. A turn is the unit the transcript grows by, and therefore the unit the bill grows by, because step 1 re-sends the whole transcript on every request. The playground below exists mostly to make that sentence concrete.

Two names matter and they are not synonyms. agent_end closes one run: the assistant produced a response with no tool calls. agent_settled is stronger: no automatic work remains — no retry pending, no compaction scheduled, no steering message queued, no follow-up waiting. A run can end while the agent is not settled, and that gap is where four of the mechanics on this page live.

Compaction is the loop's answer to a finite context window. It fires when the context exceeds the window minus a reserve — contextTokens > contextWindow - reserveTokens — keeps the most recent keepRecentTokens worth of the transcript untouched from the end, and replaces everything older with a summary. It is a lossy operation performed by a model, and the reserve is what leaves that model room to answer — pi's documentation says the reserve "leaves room for the LLM's response", and its default is 16,384 tokens. The playground's demo windows are scaled down, so its default reserve is smaller too.

Anatomy: four parts, and which one you can change

The loop

The loop is small and unglamorous: it is a while whose only decision is whether the last assistant message asked for tools. Everything people find mysterious about agents — the retries, the compaction, the interrupts — happens around that decision, not inside it. Auto-retry wraps the provider call. Compaction runs before a request. Steering and follow-ups are queued messages that decide whether the loop may stop.

What the loop does not do is verify the model's work, keep a goal alive, or notice that it is looping. Those are either prompts, or tools the model may call, or your own code outside the harness.

The tool protocol

Each tool declares its arguments as a TypeBox schema, and the harness validates every call against that schema before execute() runs. A malformed call never reaches the tool. The built-ins are read, bash, powershell, edit, write, grep, find and ls; the default allowlist is read, bash, edit and write. A run's allowlist comes from -t/--tools, from settings, or from a subagent's own declaration — and a tool that is not on it is not offered to the model at all.

Two behaviours are worth knowing because they shape what a failure looks like. Errors are thrown and returned to the model as a tool result with isError: true — a failing tool does not crash the run, it hands the model a bad result and the loop continues. And a tool can return terminate: true, which does not stop the batch: every call in it still executes and every result is still appended. What changes is the next step — the harness skips its automatic follow-up model request, and only when every completed tool in that batch returned terminate: true (shouldTerminateToolBatch is an every() over the finished calls). One tool asking to terminate is a vote, not a veto.

The consequence is that "the tool failed" and "the model knows the tool failed" are different facts. The harness guarantees the second one only.

Prompt assembly

Two layers, not one list. The system prompt is built from Pi's base instructions and the context files it discovers (AGENTS.md and CLAUDE.md up the directory tree; SYSTEM.md replaces the base text, APPEND_SYSTEM.md adds to it, and --append-system-prompt adds one more from the command line, with the trusted project .pi/ copy taking precedence). The request carries more beside that prompt: the tool definitions and the skill descriptions. Full skill instructions load on demand, and extensions can add instructions or transform the context before it is sent. Lanes add one more layer above all of it: roles/common.md plus roles/<role>.md are assembled into the role text before the harness ever sees it.

The schematic version — base prompt, context files, role text, tool schemas, skill descriptions, in that order — is the mental model this page and its playground use. The source is the authority on the order, and it counts tools and skills as request-carried rather than as prompt steps.

Either way, a tool allowlist change is also a prompt change: every tool definition is JSON Schema in the context window. Drop write and the request gets smaller and the model cannot call it; add grep and the request gets bigger and the tool appears. The playground prices that (an approximation, not a measurement), because it is easy to forget that an allowlist is not free.

Isolation, stated plainly

There is no sandbox and there is no container: every tool runs with the user's operating-system permissions (correction 1 says what follows from that). What this fleet has instead is operational isolation, and it is worth naming precisely because the word "isolation" invites the wrong inference:

MechanismWhat it actually doesWhat it does not do
Git worktreesEach lane works in its own checkout on its own branch, so two lanes cannot edit the same files or the same working tree.Does not restrict what a process may read or write elsewhere on the disk.
Role tool allowlistsA reviewer lane is given no write and no edit, so it cannot change the tree through the tool protocol.Does not stop a bash call from writing the same file. It is a policy about tools, not a permission boundary.
Branch ownershipOne writer per branch; a reviewer never pushes to the writer's branch.Does not prevent a force-push if the credentials allow it.
The reaperKills orphaned processes and browsers left by a lane that died.Does not bound what a live lane may do while it runs.

Read that table as a list of conventions enforced by code you control, not as a security boundary enforced by the kernel. If you need the second thing, you need a container, a VM or a separate machine.

    Plugins: the surface an extension actually gets

    Everything above was the harness as a product. This section is the harness as an API. The version under discussion is 0.87.1, and the names below are the names in its dist/ and its docs/: extensions.md for the surface, and rpc-commands.md plus sdk.md for the two ways to drive it without a terminal.

    An extension is a module with one default export: a factory that receives pi and registers what it wants to be called for. There is no manifest, no config file and no sandbox to configure.

    export default function (pi) {
  const stop = pi.on("tool_call", (event) => {
    if (event.toolName === "edit" || event.toolName === "write") {
      return { block: true, reason: "this lane reviews; it does not write" };
    }
  });
  // stop() unsubscribes this handler. The extension itself stays loaded: there is
  // no way to unload one plugin short of rebuilding the whole runtime.
}

    That sample is the whole shape. What makes it worth writing down is not the factory but the two objects it is handed, and the fact that they are not a boundary.

    Two objects: the API, and the context of one dispatch

    You getWhat is in it
    pi (ExtensionAPI)on(hook, handler) — which returns an unsubscribe — plus the registration calls (registerTool, registerCommand, registerShortcut, registerFlag, registerMessageRenderer, registerMarkdownTransformer, registerEntryRenderer, registerProvider / unregisterProvider), the session and state calls (sendMessage, sendUserMessage, appendEntry, setSessionName / getSessionName, setLabel), exec, the live getters and setters (getFlag, getActiveTools / getAllTools / setActiveTools, getCommands, setModel, getThinkingLevel / setThinkingLevel), and the shared events bus. setActiveTools is the one the deactivation control below is modelled on.
    ctx (ExtensionContext), per dispatchui, mode, hasUI, cwd, sessionManager (read-only), modelRegistry, model, scopedModels, thinkingLevel, isIdle(), isProjectTrusted(), signal, hasPendingMessages(), getContextUsage(), compact(), getSystemPrompt(), abort(), shutdown().
    ctx in a command handlerThe same, plus waitForIdle, newSession, fork, navigateTree, switchSession, reload. These are command-only because calling them from a lifecycle handler can deadlock the loop.

    That last row is the design tell. The powerful verbs — replace the session, fork, move the leaf, rebuild the runtime — are not in the context of a lifecycle hook. A hook can ask for things; a command handler can do them. If you find yourself wanting ctx.fork() inside a turn_end handler, the shape of the API is telling you that you want a command.

The rest are instrumentation, and instrumentation is most of what a working extension does.

    The registry: add works, replace is undocumented, removal does not exist

    registerTool writes into the extension's tool map and then calls the runtime's tool-list refresh, so a tool is callable as soon as it is registered: at load, or later from a handler or a command. The refresh is only needed post-bind, which is exactly why a registration made from a command handler takes effect without a reload. The shipped dynamic-tools example does both halves: its own header describes it as "registering tools after session initialization", it registers one tool during session_start, and it registers more at runtime from a /add-echo-tool command. The interesting part is what happens around the edges of that.

    What you wantPossible?HowThe catch
    Add a tool while the process runsYespi.registerTool(...), at load or later from a handler or a commandThe runtime's tool list is refreshed post-bind, so the tool is callable as soon as it is registered. The shipped dynamic-tools example registers at session_start and again at runtime from /add-echo-tool.
    Replace a tool by nameWorks, undocumentedregisterTool again with the same nameIt is a map set, so the new definition wins — but no documentation promises it and no diagnostic reports it.
    Shadow a built-inYesregister a tool with a built-in's nameExtension tools shadow built-ins by name, silently.
    Beat another extension to a nameFirst-loaded winsbe earlier in the load orderSilently. Tool names are the one registry without a conflict diagnostic; shortcuts and commands have diagnostics.
    Remove a toolNo—There is no unregisterTool: zero hits across this version's dist/, docs/ and examples/. setActiveTools deactivation is the supported thing, and the tool stays registered.
    Not offer a tool at allYes, at constructiontools / noTools / excludeToolsA name that is not allowed is never in the schema, so the model cannot call it — that is a session-level decision, not a runtime one.

    So "live tool mutation" is not one capability, it is three. Adding is real. Replacing works because a map is a map. Removing is not in the API at all, and the two things that look like it are not it: setActiveTools changes what the model is offered while the definition stays in the registry, and deleting the extension file only takes effect on a reload of the whole runtime. The explorer below has a button for the removal, so you can watch it find nothing.

    What an extension is not

    An extension is code the harness calls. It is not a sandbox, and the API does not pretend otherwise:

    • Same operating-system permissions. A tool registered by an extension runs where the process runs, with the process's credentials.
    • It can read everything the harness can. Prompts, tool calls and their arguments, tool results, files, session history, and any credential the process holds. A redaction plugin is a promise, not an enforcement.
    • It gets a read-only view of the session. ctx.sessionManager is exposed, but the verbs that replace a session are command-only.
    • It is not isolated from other extensions. One extension can shadow another's tool name, and load order is the only arbitration.

    Errors are handled generously, with two exceptions that matter. A handler that throws is caught, and the failure becomes an extension_error record — the loop continues. But a failure in a tool_call handler blocks the tool, because the harness would rather not run a tool than run one it could not check. And a throw inside a tool's own execute() becomes an error result for the model, which is the same shape as any other tool failure.

    /reload: one command, three audiences

    /reload reloads keybindings, extensions, skills, prompt templates, themes and context files. It is also the sharpest example on this page of a feature that exists and is still not available where you need it.

    AudienceCan it reload?Why
    The interactive TUIYes/reload is a TUI command. It re-reads the extension set and rebuilds the runtime in place.
    A process driven over RPCOnly through an extension commandThe RPC command list in rpc-commands.md has no reload command. The one route is an extension command handler calling ctx.reload() — which means the extension you want to reload has to be the thing that reloads.
    An embedder binding extensions without command actionsNo — silentlyIf the host does not bind command actions, ctx.reload() resolves against a no-op handler. The fleet's SDK host binds extensions this way, so a reload there is a silent no-op rather than an error.

    What a reload actually does is worth being precise about, because three wrong versions of it are in circulation. It shuts the runtime down with session_shutdown { reason: "reload" }, re-imports every extension with the module cache cleared (jiti runs with moduleCache: false), and starts again with session_start { reason: "reload" }. The transcript is preserved — this is not a new session — and the process keeps running, so it is not a restart either. What it is not is per-plugin: there is no way to reload one extension. Everything is re-imported, which is why every pi and ctx object captured before the reload is stale, and why the runtime tells you not to touch a ctx after await ctx.reload().

    One more asymmetry, because it explains a design choice: a tool cannot reload the runtime. Tools are handed an ExtensionContext, which has compact() and getContextUsage() but no reload(). The documented workaround is to queue a follow-up command and let a command handler do it — the same "hooks ask, commands act" split as above.

    Space and time: where a run lives, and what it can revisit

    The loop is one process with one transcript, so it is easy to talk about "the agent" as a thing that is simply there. It is not: it has a place on the filesystem, and it has a history it can move around in. Two axes, and most of the ways multi-agent systems go wrong are one axis being mistaken for the other.

    The spatial axis: what is a boundary and what is a convention

    This fleet says "lane" a lot. A lane is not a container. What actually separates two lanes is a short list, and only the first three items on it are enforced by something other than text:

    BoundaryHard or convention?What actually enforces it
    One pi process per laneHardThe operating system. Two lanes are two processes with separate memory; a tool call in one cannot touch the other's loop.
    One session file per sessionHardThe history lives in one file, and a fork writes a second file. That is why a replay cannot damage the original.
    The tool allowlistHard for the protocolA tool that is not offered is not in the schema and the loop cannot call it. It says nothing about bash, which can write the same bytes with no tool involved.
    A git worktreeConventionOne checkout per branch keeps two lanes from editing the same files. It does not fence processes, and it is not a permission.
    The working directoryConvention, and the weakest oneThe harness is launched with cwd set to the journal directory for every lane; the worktree arrives as FLEET_WORKDIR in the prompt text. "Where am I" is a sentence the model is told, not a syscall that constrains it.
    Role separationConventionRole text plus an allowlist: a reviewer gets no write and no edit and is told not to shell out. Enforced by code around the tool and by instructions inside the prompt.
    A subagentHard for the process, and not resumableThe shipped subagent example runs --mode json -p --no-session: a one-shot child process with no session to return to. Calling it a "nested resumable session" would be wrong on both words.

    Two consequences, and both are load-bearing. First: a plugin loaded in two processes is two independent plugins — hook state is per process, and the load order in one lane says nothing about the other. Second: the only things two lanes genuinely share are the ones with a hard boundary of their own — a git remote and the beads database. Everything else that looks shared is two copies plus a convention about who writes when.

    The temporal axis: a tree, not a transcript

    A session file is a tree. Every entry has an id and a parentId, and the active branch — the path from the root to the current leaf — is what the model is sent. Not the tree: the branch. That one sentence is the whole mechanism behind re-entry, replay and compaction, and it is also the sentence most descriptions of "agent memory" get wrong.

    • Re-entry is real. /tree moves the leaf within the same file. Submit a different message at that point and you have a second branch; the first is not erased, because nothing was ever a linear log to truncate.
    • Replay is real. /fork writes a new session file whose header names the parent session, with the branch from an earlier entry. /clone copies the active branch into a new session. The original file is untouched in both cases.
    • Leaving a branch can leave a note. Pi can summarise the branch you leave and attach that summary to the branch you enter, so the work is available without every message of it.
    • Rewind is not. There is no undo. Moving the leaf changes what happens next; it does not change what happened.

    Compaction is the same idea applied to one dimension. It writes a new entry of type compaction holding the summary, tokensBefore, and firstKeptEntryId; when the context is rebuilt, everything before firstKeptEntryId is replaced by the summary and the entries from it onwards are sent as they are. The raw entries stay in the file. A "retain-none" compaction is the edge case: it stores its own id in firstKeptEntryId, so no preceding entry survives into the context, and the file is still whole.

    context_edit is the third member of the family, and it is the one most easily misread. It appends an entry that changes what the model sees from that point on — it is branch-relative, and it does not rewrite history. A tool result you edited out with a context edit is still in the file, and a fork from before the edit still sees it.

    Put together: the harness has a real sense of "where" (process, file, allowlist) and a real sense of "when" (tree, branch, compaction cut). What it does not have is a way to make either of them invisible. Every rewrite leaves an entry; every boundary is either a kernel fact or a sentence in a prompt.

    How the two compose

    SetupWhat is separateWhat is sharedWhat it is good for
    Two lanesTwo processes, two worktrees, two session files, two tool allowlistsThe git remote and the beads database — and nothing elseParallel work on one repository without a merge per tool call. Convergence happens through git, deliberately and late.
    One session forked at a turnTwo session files, two branchesOne process, one worktree, one tool setReplay: try the other repair, keep the first attempt readable, and compare afterwards without a checkout.
    One session, compactedNothing — one file, one branchEverything, including the entries the summary replacedA long run that keeps going: the model's context shrinks, the file does not.

    The mistake to avoid is using the spatial axis for a temporal problem. Restarting a process to get a fresh transcript throws away the history you might have wanted to compare against; forking a session gives you the fresh context while keeping the original file, at the cost of nothing but disk. And the reverse mistake is just as common: expecting a fork to give you isolation, when both files are in the same worktree, the same process and the same tool set.

    Plugin explorer: add a hook, deactivate a tool, fork a session

    This is a deterministic simulation of the plugin surface and the session graph. No extension is loaded, no model is called, no key is used and nothing leaves this page. plugins.js holds the scripted run and the arithmetic; explorer.js renders whatever it returns.

    Six controls, and each one is a mechanic from the two sections above:

    • Add a plugin — an extension that hooks something. Watch the load order, the dispatch count, and what that hook did to the run's numbers. A hook that only observes moves no numbers, which is the honest result and worth seeing once.
    • Offer or withhold a tool — the construction-time allowlist. A tool that is not offered is not in the schema, so the scripted assistant's call to it fails as "not offered".
    • Deactivate a tool mid-run — setActiveTools. The tool stays registered; the next call to it fails. This is labelled deactivated, not unregistered everywhere it appears, because that distinction is the whole point.
    • Guard a call — a tool_call handler returning { block: true }, with and without terminate. The two terminate options exist to show that a vote is not a veto: blocking bash votes inside a two-call batch and the loop carries on past turn 2 — until turn 4, where bash is the only call in its batch and the same vote is unanimous, so the run does stop there; blocking edit votes inside a one-call batch and the run stops at turn 3.
    • Fork the session — the chosen turn decides the prefix, a new file gets the other branch, and file A keeps the branch it abandoned.
    • Move the compaction cut — firstKeptEntryId slides down the active branch: everything above it becomes the summary, and the numbers move with it.

    Plugins, in load order

    Each button appends an extension to the load order. Hooks dispatch in that order, and the list is snapshotted when a dispatch starts — so order matters and a mid-dispatch change does not.

      This clears the explorer's own state. In a real lane the set is fixed when the runtime is built: changing it means a reload of the whole runtime, or a restart.

      Tools: offered, and active

      A tool_call guard

      terminate is a vote the loop only honours when every finalized result in the batch agrees — and the batch, not the setting, decides. Turn 2 carries two calls (bash + read), so a bash vote there is ignored; turn 4 carries a solo bash, so the same vote stops the run at turn 4; turn 3 carries a solo edit, so an edit vote stops it at turn 3.

      Space and time

      A fork writes a new session file from an earlier entry and gives it a different branch. The file that ran keeps the branch the new one left behind.

      The cut is a position in the active branch: that entry becomes firstKeptEntryId, everything before it is replaced by the summary when the context is rebuilt, and every entry stays in the file.

        Notes on this state

          What this does not model

          • The model. The scripted assistant makes the same four turns whatever you do. A real model reacts to a blocked or failed call — that reaction is model behaviour, not a harness mechanic, and inventing it here would be inventing evidence.
          • Hook side effects beyond the arithmetic. A plugin's effect is one number each: tokens redacted, tokens stamped, tokens annotated, schema tokens added, dispatches fired. Real handlers can do anything, including nothing, and the page cannot tell you which.
          • The controls' reach into the forked branch. The alternative branch taken at a fork point is rendered as executed calls with their raw token counts, whatever the guard, deactivation and offer controls say. Those controls act on the recorded run in file A; the replay is a fixed alternative path, not a second simulation.
          • Hook ordering beyond load order. Handlers within one extension dispatch in the order they were registered; the explorer models one handler per plugin.
          • Real tokenisation. Every count is a constant. A real redaction saves whatever the redacted text actually costs, which may be nothing if the model's tokeniser disagrees with my arithmetic.
          • The files on disk. The fork and the compaction are rendered as if they had been written; nothing is serialised, and tokensBefore, the compaction's systemMessage checkpoint and branch summaries are not drawn.
          • Reload. There is no button for it. A reload rebuilds the whole runtime, which is not a property of the graph — it is why the graph cannot be changed in place.

          Malleable software: what can you reshape without a deploy?

          "Malleable software" is a useful phrase only if it comes with a boundary. Here the boundary is where the value is read: per request, per runtime, at process start, or baked into the package. That gives the rungs below, and the difference between them is usually a reload or a restart, not a rewrite.

          Three verdicts, stated up front

          Applied to the three questions people actually ask about a harness like this one, the answers are not all the same shape, and two of the three are conditional:

          ClaimVerdictAt what granularity
          A plugin can be hot-swapped EXISTS The whole runtime, at once. A reload rebuilds the loop in-process — every extension re-imported, the transcript preserved — and there is no way to reload one plugin.
          Tools can be mutated live PARTIAL Add: yes — at load, or later from a handler or a command, because registerTool refreshes the runtime. Replace: works because the registry is a map, and is undocumented. Remove: no API at all — setActiveTools deactivates, and the tool stays registered.
          The prompt can be re-woven mid-run PARTIAL before_agent_start fires once per user prompt, which is a single call site per run. Per-request rewriting is context, context_with_system and before_provider_request. Re-rendering the prompt's sections between turns does not exist.

          And the things that are simply not there, said plainly because each of them is a plausible guess: there is no unregisterTool; no reload command over RPC; no way for a tool to reload the runtime itself; no way for a hook to reach a dispatch already in progress; no single terminate that stops a batch; and no sandbox around an extension.

          What that means for software you can mould live

          Sort what you want to change by what it takes to make the change visible. This is the table I would put on the wall before designing anything that calls itself malleable:

          What you want to reshapeWhat it takesWhy
          Which tools the model may use, right nowNothing — setActiveToolsThe runtime rebuilds the prompt from the active set, so the next request carries a different schema. The tool stays registered.
          What the model sees of the pastAn entry — a compaction, or a context_editBoth append to the branch. Neither deletes anything, and both are relative to the branch you are on.
          The loop's behaviour inside a requestA hook — context, context_with_system, before_provider_requestThese fire per request, which is the only place per-request behaviour can live.
          The prompt's structure between turnsCode — it does not existbefore_agent_start is one call site per user prompt. There is no per-turn prompt re-render to hook.
          A whole extension — its hooks, its tools and its commandsA reload of the runtime, or a restartThe extension set is read when the runtime is built. A reload rebuilds it in-process; a restart rebuilds it from scratch.
          The provider's wire format, the built-in tools' behaviourCode, then a restartAdapters and built-ins are the package. This is the rung where a mistake reaches every lane at once.

          The rungs

          RungWhat changesHow it takes effectWhat it costs to be wrong
          Hot The model, the thinking level, compaction (on/off or now), the active tool set, and models.json — opening /model reloads that file RPC: set_model, set_thinking_level, compact, set_auto_compaction; setActiveTools inside an extension; opening /model reloads models.json One bad run.           Reload Extensions, skills, prompt templates, themes, keybindings, context files /reload, in the TUI — or ctx.reload() from an extension command handler.           The reload rung is where most "malleable" claims go wrong in one direction or the other. It is more than the sceptics say — the runtime really is rebuilt in place, the transcript really is preserved, and it is not a restart — and less than the enthusiasts say: it is not per-plugin, it is not complete (every extension is re-imported whether you touched it or not), and in this fleet's headless lanes it is not reachable at all. Editing an extension's TypeScript and expecting the next headless run to pick it up does not work, because the extension set is read when the runtime is built and nothing in the RPC or SDK surface issues a reload. Over RPC the only route is an extension command handler calling ctx.reload(), and this fleet's SDK host binds extensions without command actions, which turns that call into a silent no-op. So the honest statement for a headless lane is "extensions are malleable with a restart", and the honest statement for the TUI is "extensions are malleable, all of them at once".

          The extensibility ladder

          The same boundary sorts the ways you can extend the harness. Roughly in order of how much of the loop you get to change:

          1. Extensions (.ts) — full access: register tools, hook events, change what the loop does.
          2. Custom providers — a new wire protocol for a new endpoint. This is an extension too, not a rung below one: pi.registerProvider() is called from an extension factory and inherits its loading, trust and reload behaviour.
          3. Custom tools (pi.registerTool) — a tool with a schema, without owning the loop.
          4. Skills (SKILL.md) — instructions and procedures the model can load; no new code paths.
          5. Prompt templates — a reusable starting prompt.
          6. models.json — a new model on an existing protocol: base URL, token limits, and which wire quirks to speak. The provider docs send you here first when the service already speaks a supported API.

          Each rung is a real product decision, not a taste. A skill that would solve the problem is better than an extension, because a skill is readable by the person who inherits it and an extension is code you now maintain. The list is also a map of where bugs hide: the further down you go, the less of the loop you own and the more the answer is "it depends on the model"; the higher up, the more it is "it depends on you".

          What is DeepSeek-specific, and what is just the harness

          Almost everything described above is generic. The loop, the tool protocol, the sessions, the transcript, compaction, retries and steering behave the same whatever endpoint pi-ai is pointed at. Only the adapter is DeepSeek's.

          ConcernWhere it livesDeepSeek-specific?
          Turn loop, agent_end, agent_settledHarness (pi-agent-core)No
          TypeBox validation, allowlists, isError, terminateHarnessNo
          Prompt assembly, context files, skillsHarness + fleet rolesNo
          Compaction thresholds and the summaryHarnessNo
          How thinking is requestedProvider adapterYes — thinkingFormat: "deepseek" emits {thinking: {type: "enabled"}}, and reasoning_effort is passed alongside it
          Whether reasoning text comes back on the assistant messageProvider adapterYes — requiresReasoningContentOnAssistantMessages, it must be echoed back
          Output length fieldProvider adapterYes — max_tokens
          Provider error classification and network pathLane host + deploymentYes — a regex over the provider's error text, and the exe.dev proxy

          One of those has a price attached, and the playground is wired to it. requiresReasoningContentOnAssistantMessages means the assistant's reasoning text must be sent back on the next request: drop it and the conversation is not merely less detailed, it is a different conversation. It also means reasoning tokens are paid for twice — as output when produced, and as input on every later request in the run, until a compaction summarises them away. The playground's thinking control is exactly that mechanic, and because more thinking also means more context it can trigger more compaction, which is why the numbers move in both directions there.

          Operational detail rather than protocol: outbound calls go through the exe.dev HTTPS proxy, which is the reason a run that works in a terminal can fail under systemd. And there is no credit-check API in play — the lane hosts classify the provider's error text with a regex (quota, rate limit, insufficient, balance, credit, payment, 402, 429) and, after two consecutive such errors, the lane host cools that provider down for the whole VM and moves the lane to the next model in its role's rotation. That is how "out of credit" and "rate limited" are told apart here: both arrive as an error string, and the lane acts on the words.

          Honest limits, stated as corrections

          Six claims about harnesses like this one are common, plausible, and wrong. Each one is wrong in a way that changes what you should build.

          1. "The agent runs in a sandbox."

          There is no sandbox and no container. Tools execute with the user's operating-system permissions. Schema validation is not a security boundary; it is a shape check. The isolation in this fleet is operational — worktrees, role tool allowlists, branch ownership, the reaper — and every one of those is a convention enforced by code that runs around the tool, not by the kernel around the process. A role whose allowlist omits write is a role that has agreed not to write; give it bash and it can still write.

          2. "Edit the extension and the next run picks it up."

          False in headless RPC, and the near-miss is what makes it confusing. The extension set is read when the runtime is built, and a reload does rebuild it — but /reload is a TUI command. The RPC command list has no reload, so over RPC the only route is an extension command handler calling ctx.reload(), and a host that binds extensions without command actions resolves that call against a no-op. This fleet's SDK host binds them that way, so in a systemd-managed headless lane changing an extension's TypeScript means restarting the process. Plan the restart into the change instead of being surprised by it — this is the single most common way a "malleable" tool turns out to be "malleable after a deploy".

          3. "DeepSeek takes the same reasoning settings as OpenAI."

          It does not, and the mistake is quiet. Thinking is switched on by a thinking object that the deepseek thinking format emits; reasoning_effort travels alongside it rather than replacing it (the adapter does not exclude DeepSeek from effort support), and the length field is max_tokens, not max_completion_tokens. Point an OpenAI-format model entry at DeepSeek and the effort field still goes out with no thinking object at all: the request is accepted, nothing errors, and the model is not thinking the way you asked. Silent accepted-but-ignored fields are exactly what a schema assertion in your own test suite is for.

          4. "The reviewer can't write, so the reviewer is safe."

          A reviewer lane with no write and no edit is restricted by tool allowlist omission plus prompts. That is a good and cheap restriction, and it is not an operating-system block. If a reviewer is given bash, the shell can write. The honest version of the claim is: "the reviewer has no way to write through the tool protocol, and its instructions say not to try any other way". If you need more than that, take the tools away or run it somewhere with real permissions.

          5. "One tool returning terminate ends the run."

          It does not, and it does not even end the batch. Every call in the batch still executes and every result is still appended; what changes is the step after it. The harness skips its automatic follow-up request only when every finalized result in that batch asked to terminate, so a single vote inside a two-call batch is ignored. The explorer has the setting in both shapes on purpose, and it also shows the twist: blocking bash votes inside turn 2's two-call batch and the run carries on — but turn 4 is a solo bash, so that batch is unanimous and the run stops there. Blocking edit votes inside a one-call batch and it stops at turn 3. Whether a vote counts is a property of the batch, never of the setting.

          6. "Compaction deletes history."

          It appends. A compaction is a new entry holding the summary, tokensBefore and a firstKeptEntryId; when the context is rebuilt, the entries before that id are replaced by the summary and the raw entries stay in the file. A retain-none compaction stores its own id in firstKeptEntryId so nothing before it survives into the context — and the file is still whole. What compaction deletes is context, not history, and a fork from before the compaction still sees everything.

          What this page does not claim

          The token counts in both simulations are constants chosen so the mechanics are visible at a few thousand tokens; they are not measurements of a real run. The demo context windows are small on purpose for the same reason. Real billing, real latency, provider caching, tokeniser differences and model behaviour are all outside the simulations — including the scripted assistant in the explorer, which does not react to a blocked or failed call the way a model would. Nothing here was benchmarked: the page describes a harness this fleet runs and the code you can read in it, not a performance claim about any model.
