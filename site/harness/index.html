The harness, and software you can reshape

An agent is a loop, a tool protocol and a prompt, wrapped in whatever isolation you actually built. This page takes the DeepSeek harness running in this fleet apart, and then hands you the controls: a simulated run you can re-price by changing one setting at a time.

This page calls nothing. The playground below is a deterministic simulation: no key, no network, no model. Every number it shows is computed from the controls and a scripted transcript. The playground section says exactly which mechanics it does and does not model.

What the harness actually is here

The harness is @earendil-works/pi-coding-agent, with pi-agent-core and pi-ai underneath it. It is not a chat application and it is not a sandbox. It is a Node process that owns four things: the loop that decides when to call the model again, the tool registry that turns the model's requests into local processes, the transcript that is re-sent on every request, and the prompt assembly that decides what the model is told.

In this fleet it runs headless, under systemd, with no terminal attached. Its parent process is remote/lane-host.mjs, which speaks to it over JSON lines over a pipe: one JSON object per line in, one per line out. The model itself is a remote HTTP endpoint (DeepSeek, reached through the exe.dev HTTPS proxy). Everything else on this page — the loop, the tools, the transcript, the compaction, the prompts — is local code you can read, restart and change.

That split is the whole point. Swapping the model is a configuration change. Swapping the loop is a code change. The interesting engineering is all in the second category, and most writing about agents collapses the two.

The loop, in plain language

  1. Build a prompt: the base instructions, the lane's role text, the project's context files, the task, the transcript so far, and the JSON Schema of every tool this run may use.
  2. POST it to the provider. The reply is text, tool calls, or both.
  3. If there are tool calls: validate each argument object against its TypeBox schema, run the tools locally under your operating-system permissions, append the results to the transcript.
  4. If the assistant made any tool call, go back to step 1. If it made none, the run is over.

One turn is one assistant response plus the tool calls it carried plus their results — appended, not replaced. A turn is the unit the transcript grows by, and therefore the unit the bill grows by, because step 1 re-sends the whole transcript on every request. The playground below exists mostly to make that sentence concrete.

Two names matter and they are not synonyms. agent_end closes one run: the assistant produced a response with no tool calls. agent_settled is stronger: no automatic work remains — no retry pending, no compaction scheduled, no steering message queued, no follow-up waiting. A run can end while the agent is not settled, and that gap is where four of the mechanics on this page live.

Compaction is the loop's answer to a finite context window. It fires when the context exceeds the window minus a reserve — contextTokens > contextWindow - reserveTokens — keeps the most recent keepRecentTokens worth of the transcript untouched from the end, and replaces everything older with a summary. It is a lossy operation performed by a model, which is why the reserve exists: the reserve is the room the summary request itself needs.

Anatomy: four parts, and which one you can change

The loop

The loop is small and unglamorous: it is a while whose only decision is whether the last assistant message asked for tools. Everything people find mysterious about agents — the retries, the compaction, the interrupts — happens around that decision, not inside it. Auto-retry wraps the provider call. Compaction runs before a request. Steering and follow-ups are queued messages that decide whether the loop may stop.

What the loop does not do is verify the model's work, keep a goal alive, or notice that it is looping. Those are either prompts, or tools the model may call, or your own code outside the harness.

The tool protocol

Each tool declares its arguments as a TypeBox schema, and the harness validates every call against that schema before execute() runs. A malformed call never reaches the tool. The built-ins are read, bash, powershell, edit, write, grep, find and ls; the default allowlist is read, bash, edit and write. A run's allowlist comes from -t/--tools, from settings, or from a subagent's own declaration — and a tool that is not on it is not offered to the model at all.

Two behaviours are worth knowing because they shape what a failure looks like. Errors are thrown and returned to the model as a tool result with isError: true — a failing tool does not crash the run, it hands the model a bad result and the loop continues. And a tool can return terminate: true, which ends the current batch immediately: the remaining calls in that batch are not executed and their results are not produced. That is how a single call can shorten a turn.

The consequence is that "the tool failed" and "the model knows the tool failed" are different facts. The harness guarantees the second one only.

Prompt assembly

The prompt is assembled, in order, from: a base prompt; the project's hierarchical context files (AGENTS.md and CLAUDE.md, discovered up the directory tree); anything passed as --append-system-prompt; the tool definitions; and the skill descriptions. Lanes add one more layer: roles/common.md plus roles/<role>.md are assembled into the role text before the harness ever sees it.

This is why a tool allowlist change is also a prompt change: every tool definition is JSON Schema in the context window. Drop write and the prompt gets smaller and the model cannot call it; add grep and the prompt gets bigger and the tool appears. The playground prices that, because it is easy to forget that an allowlist is not free.

Isolation, stated plainly

This harness is not a sandbox and there is no container. Tools run with the user's operating-system permissions. A bash call can read your home directory, your SSH keys and your environment; an edit call can write anywhere that user can write. Nothing in the loop, the schema validation or the transcript interception changes that. Schema validation checks that a call is shaped correctly, not that it is safe.

What this fleet has is operational isolation, and it is worth naming precisely because the word "isolation" invites the wrong inference:

MechanismWhat it actually doesWhat it does not do
Git worktreesEach lane works in its own checkout on its own branch, so two lanes cannot edit the same files or the same working tree.Does not restrict what a process may read or write elsewhere on the disk.
Role tool allowlistsA reviewer lane is given no write and no edit, so it cannot change the tree through the tool protocol.Does not stop a bash call from writing the same file. It is a policy about tools, not a permission boundary.
Branch ownershipOne writer per branch; a reviewer never pushes to the writer's branch.Does not prevent a force-push if the credentials allow it.
The reaperKills orphaned processes and browsers left by a lane that died.Does not bound what a live lane may do while it runs.

Read that table as a list of conventions enforced by code you control, not as a security boundary enforced by the kernel. If you need the second thing, you need a container, a VM or a separate machine — and then the harness is the same harness, just somewhere safer.

    Malleable software: what can you reshape without a deploy?

    "Malleable software" is a useful phrase only if it comes with a boundary. Here the boundary is where the value is read: per request, at process start, or baked into the package. That gives three rungs, and the difference between them is usually a restart, not a rewrite.

    RungWhat changesHow it takes effectWhat it costs to be wrong
    Hot The model, the thinking level, compaction (on/off or now), and models.json on the next /model RPC: set_model, set_thinking_level, compact, set_auto_compaction; models.json is re-read on /model One bad run. The process keeps running and the next request uses the new value.
    Restart CLI flags and environment, the set of extensions loaded in headless RPC, and settings.json Restart the process; the values are read at startup. An interrupted run and a cold context. Nothing is lost that was not in the transcript.
    Code change Provider adapters, and the behaviour of the built-in tools Edit and redeploy the package, then restart. A review, a CI run and a version to roll back to. This is the rung where you can break every lane at once.

    The middle rung is where most "malleable" claims quietly fail. Editing an extension's TypeScript and expecting the next headless run to pick it up does not work: the extension set is read when the process starts. Only the interactive TUI has a /reload. So the honest statement is "extensions are malleable with a restart", not "extensions are malleable".

    The extensibility ladder

    The same boundary sorts the ways you can extend the harness. Roughly in order of how much of the loop you get to change:

    1. Extensions (.ts) — full access: register tools, hook events, change what the loop does.
    2. Custom tools (pi.registerTool) — a tool with a schema, without owning the loop.
    3. Skills (SKILL.md) — instructions and procedures the model can load; no new code paths.
    4. Prompt templates — a reusable starting prompt.
    5. Custom providers — a new wire protocol for a new endpoint.
    6. models.json — a new model on an existing protocol: base URL, token limits, and which wire quirks to speak.

    Each rung is a real product decision, not a taste. A skill that would solve the problem is better than an extension, because a skill is readable by the person who inherits it and an extension is code you now maintain. The ladder is also a map of where bugs hide: the lower the rung, the more the answer is "it depends on the model"; the higher, the more it is "it depends on you".

    What is DeepSeek-specific, and what is just the harness

    Almost everything described above is generic. The loop, the tool protocol, the sessions, the transcript, compaction, retries and steering behave the same whatever endpoint pi-ai is pointed at. Only the adapter is DeepSeek's.

    ConcernWhere it livesDeepSeek-specific?
    Turn loop, agent_end, agent_settledHarness (pi-agent-core)No
    TypeBox validation, allowlists, isError, terminateHarnessNo
    Prompt assembly, context files, skillsHarness + fleet rolesNo
    Compaction thresholds and the summaryHarnessNo
    How "thinking" is requestedProvider adapterYes — a thinking object, not OpenAI's reasoning_effort
    Whether reasoning text comes back on the assistant messageProvider adapterYes — it must be echoed back
    Output length fieldProvider adapterYes — max_tokens
    Credit check and network pathAdapter + deploymentYes — a balance endpoint and the exe.dev proxy

    The three wire differences that actually bite when you wire a new model up:

    1. Thinking is a mode, not an effort. The adapter uses thinkingFormat: "deepseek" and emits {thinking: {type: "enabled"}}. Copying an OpenAI config and setting reasoning_effort produces a request that is accepted and quietly does not enable thinking. There is no error, which is the worst kind of wrong.
    2. Reasoning content is state you have to keep. requiresReasoningContentOnAssistantMessages: true means the assistant's reasoning text must be sent back on the next request. Drop it and the conversation is not merely less detailed, it is a different conversation. It also means reasoning tokens are paid for twice: as output when produced, and as input on every later request in the run, until a compaction summarises them away. The playground's thinking control is wired to exactly that mechanic — and because more thinking also means more context, it can trigger more compaction, which is why the numbers move in both directions there.
    3. The length field is max_tokens. Not max_completion_tokens. Sending the OpenAI field is another silent no-op: the request succeeds, the cap is not applied where you expected, and the truncation you asked for does not happen.

    Two operational ones: the adapter exposes DeepSeek's balance endpoint, which is how a lane can tell "out of credit" from "rate limited" before a run fails halfway; and outbound calls go through the exe.dev HTTPS proxy, which is a deployment fact rather than a protocol one — but it is the reason a run that works in a terminal can fail under systemd.

    Honest limits, stated as corrections

    Four claims about harnesses like this one are common, plausible, and wrong. Each one is wrong in a way that changes what you should build.

    1. "The agent runs in a sandbox."

    There is no sandbox and no container. Tools execute with the user's operating-system permissions. Schema validation is not a security boundary; it is a shape check. The isolation in this fleet is operational — worktrees, role tool allowlists, branch ownership, the reaper — and every one of those is a convention enforced by code that runs around the tool, not by the kernel around the process. A role whose allowlist omits write is a role that has agreed not to write; give it bash and it can still write.

    2. "Edit the extension and the next run picks it up."

    False in headless RPC. The extension set is read when the process starts; only the interactive TUI's /reload re-reads it. In a systemd-managed headless lane, changing an extension's TypeScript means restarting the process. Plan the restart into the change instead of being surprised by it — this is the single most common way a "malleable" tool turns out to be "malleable after a deploy".

    3. "DeepSeek takes the same reasoning settings as OpenAI."

    It does not. Thinking is enabled by a thinking object through the deepseek thinking format, not by OpenAI's reasoning_effort, and the output cap is max_tokens, not max_completion_tokens. Both mistakes fail silently: the request is accepted and the setting does nothing. Silent accepted-but-ignored fields are exactly what a schema assertion in your own test suite is for.

    4. "The reviewer can't write, so the reviewer is safe."

    A reviewer lane with no write and no edit is restricted by tool allowlist omission plus prompts. That is a good and cheap restriction, and it is not an operating-system block. If a reviewer is given bash, the shell can write. The honest version of the claim is: "the reviewer has no way to write through the tool protocol, and its instructions say not to try any other way". If you need more than that, take the tools away or run it somewhere with real permissions.

    What this page does not claim

    The token counts in the simulation are constants chosen so the mechanics are visible at a few thousand tokens; they are not measurements of a real run. The demo context windows are small on purpose for the same reason. Real billing, real latency, provider caching, tokeniser differences and model behaviour are all outside the simulation. Nothing here was benchmarked: the page describes a harness this fleet runs and the code you can read in it, not a performance claim about any model.

    Where this comes from

    The claims above describe the harness as this fleet has it configured, read from its own source rather than from a public announcement: the package @earendil-works/pi-coding-agent and its pi-agent-core and pi-ai dependencies; the lane host in remote/lane-host.mjs; the lane role prompts assembled from roles/common.md and roles/<role>.md; and the provider adapter whose DeepSeek settings are named in the table above.
