dsh, Cordis, and software you can reshape

DeepSeek Harness is an open-source agent harness with no privileged core: the loop, the tool registry, the session log, the model adapters and the permission policies are all plugins on one context tree. This page reads that tree out of the source — the framework underneath it, the effect and coeffect machinery that makes a plugin removable, the step-and-turn model that runs on top — and then hands you the controls, so you can mount, swap and unwind the registrations yourself.

No model is called. The playground is a deterministic model of the Cordis and dsh mechanics this page describes: no key, no network, no model, no plugin loaded. It computes every count and every state word from the controls, and its “what this does not model” list says exactly where it stops.

Part 1 — How dsh is built with Cordis

1. What dsh is

DeepSeek Harness (dsh) is an open-source agent harness from DeepSeek AI, MIT-licensed, written in TypeScript, and in developer preview — its README says so in capitals: “THERE WILL BE COMPATIBILITY-BREAKING CHANGES.” You start it with npx @deepseek-ai/dsh web, which serves a Web UI on http://127.0.0.1:3080 by default. Everything on this page is read from a clone of github.com/deepseek-ai/deepseek-harness at commit fcc0ad4, not from an announcement.

Two sentences from the README are the whole thesis, and the rest of this page is their consequences:

“It is built on an everything-is-a-plugin architecture and powered by [Cordis]” — README.md:7

Cordis is not a library dsh happens to use. It is vendored into the repository as six packages — @deepseek-ai/cordis 4.1.0, @deepseek-ai/cordis-plugin-loader 1.1.0, @deepseek-ai/cordis-plugin-hmr 1.1.0, @deepseek-ai/cordis-plugin-group 1.1.0, @deepseek-ai/cordis-plugin-include 1.1.0 and @deepseek-ai/cordis-plugin-timer 1.2.0 — and the product is a composition of plugins on top of it. The stack, from the metal up:

Launcher@deepseek-ai/dsh — dsh --profile web composes the tree, then boots it
Profilea named composition in the Harness home: the bundles it stacks, out-of-tree plugins, and the user's own cordis.patch.yml
Bundlesdsh-base first, then dsh-web-app / dsh-headless / dsh-sdk-app / dsh-acp-app / dsh-sdk-minimal
Pluginsthe model adapters, tools, session log, sandbox policy, settings, creds, telemetry, the agent loop
Cordiscontext tree, services, typed events, reversible effects — the framework every row above is a plugin of

The words are the architecture doc's, not a diagram of my own: a profile is “a named composition stored in the Harness home… it lists the bundles it stacks, holds any out-of-tree plugins it installs, and keeps the user's own cordis.patch.yml”, and a bundle “is a distribution format for Cordis config rows and the code they mount, so whatever it inserts stays patchable by the layers above it” (docs/architecture.md). dsh-base is “the shared first layer of the web, headless, sdk, and acp profiles”: model adapters, tools, persistence, sandbox and approval policy, settings, credentials, telemetry. Each of those is a plugin on the same context tree as the next.

2. Spatiotemporal composability, in the framework's own terms

Cordis is the implementation of a paper by Yifan Shi, Wei Zhang and Tianyi Cui (Peking University and DeepSeek-AI): A Programming Paradigm for Spatiotemporal Composability (arXiv 2608.25512). The title is where the word comes from, and the abstract defines both axes — and reading both definitions literally is what keeps the word honest. Read them:

“temporal composability, the ability to completely revert a component's side effects upon removal, and spatial composability, the ability to declare and reactively manage inter-component dependencies.”

“we formalize revertible effects, in which every context transformation carries an inverse that the runtime holds, establishing temporal composability local to one component. We formalize reactive coeffects, in which every context change is classified against a component's coeffect specification to drive its activation and deactivation, establishing spatial composability local to one component.”

Then the two are unified, which is the actual claim of the paper:

“We then unify the effect context and the coeffect context into a single context type and mediate every effect and coeffect through it, yielding a discipline we call the context paradigm; the mediation induces an observational equivalence up to which the effects of distinct components interleave without disturbing one another.”

So the trick is not two systems. There is one context type carrying both halves: an effect context that remembers what each component changed so removal can invert it (time), and a coeffect context that holds each component's declaration of what it requires, checked against every change, so the component can be switched on and off (space). The paper's contributions, in its own abstract's terms, are a calculus of dynamic composition and a metatheory carrying “spatiotemporal composability from a single component to a whole system of interleaved components”; Cordis is described as “a meta-framework of spatiotemporal composability that provides a core library with effect tracking and coeffect resolution, as well as a declarative component loader with configuration reconciliation and hot module replacement.”

AxisThe paper's wordWhat it buys a programWhere dsh shows it
Temporalrevertible effects — “every context transformation carries an inverse that the runtime holds”A component can be removed completely: its registrations, listeners and services go away because each carried an inverse.Unmounting a plugin, restarting a fiber, hot-swapping a module (§4, §8)
Spatialreactive coeffects — “every context change is classified against a component's coeffect specification to drive its activation and deactivation”A component declares what it needs and never has to be sequenced by hand: it activates when the requirement is met and deactivates when it is not.inject, ctx.<key> service claims, per-agent scopes (§3, §6)

Two things it does not mean. “Spatiotemporal” here is not sandboxing, and it is not replay. Sandboxing confines a process's file access; the Cordis paper is about when a component may be active and how its departure is undone. Replay reconstructs a session from a log; the paper's temporal axis is the runtime holding an inverse for each registration, not re-running history. dsh has both sandboxes and an append-only session log, and both are separate mechanisms from the one this word names. Sourcing note: only the paper's abstract page was reachable from here (the arXiv HTML view 404s, and the PDF's subset-encoded fonts did not extract to text), so the formal claims above are quoted from the abstract and I have not paraphrased theorem statements I could not read. The mechanisms themselves are verifiable in the vendored source, which is what §4 does.

3. The Cordis context tree: Context, Service, Plugin

Three concepts carry the whole framework, and the vendored source states each of them in a comment above the code.

ConceptThe source's own wordsWhat it is in practice
Context “Root and child dependency containers for Cordis plugins. A context is a proxy: normal property reads go through the service resolver, while extend(), isolate(), and intercept() create scoped child contexts without mutating their parent.” (vendor/cordis/src/context.ts) Every API is reached through ctx: ctx.tools, ctx.on(...), ctx.effect(...), ctx.plugin(...). There is one root context, and children are cheap shadows of it.
Service “Base class for services that expose a named API on ctx. Subclasses call super(ctx, name) from their constructor. The service is registered immediately and is automatically removed with the owning fiber.” (vendor/cordis/src/service.ts) A stable ctx.<key> that other plugins find by name: ctx.sessions, ctx.tools, ctx.llm, ctx.shell.
Plugin “A plugin is a object that implements Service. It can be a function with optional inject and apply(ctx) fields, or a Service subclass whose lifecycle Cordis mounts into the current context.” (docs/cordis-primer.md) The unit of distribution and of removal. A plugin loaded once is a fiber: “one loaded plugin instance: its lifecycle state, validated config, and registered effects” (docs/cordis-api/fiber.md).

The five ideas the primer teaches fit on one screen, and the fourth is a table worth reproducing exactly, because the dispatch mode is part of an event's contract rather than a detail of its call site:

ModeAwaited?Dispatch orderHas return value?
emitNolisteners observe in registration orderNo
waterfallNolisteners observe in registration orderYes
parallelYesall listeners observe the event in parallelNo
serialYeslisteners observe in registration orderYes
bailNolisteners observe in registration order until one bailsYes

A waterfall is around-middleware: “A listener receives (...args, next). Call next() to delegate the possibly wrapped result to the next service; return without next() to short-circuit.” That sentence is why dsh can veto a claimed message from a plugin without the loop knowing the plugin exists.

And the line that makes the spatial axis concrete, from the bundle that composes the shipped product: “Row order carries no load semantics (activation is service-availability driven)” (packages/bundle/base/cordis.patch.yml). A config file lists 100+ rows in whatever order reads well; what decides when each activates is the services it declares it needs. There is no boot sequence to get right.

4. The runtime kernel, read from the vendored source

This section is the one a reviewer should check hardest, so every claim carries a file and a line. Everything below is from vendor/cordis/src/ at fcc0ad4.

Registration is an effect, and the effect holds the inverse

ctx.effect(execute, label) runs execute immediately and collects the disposer it produces. The doc comment on the method is the contract:

“execute runs immediately; the disposers it produces are collected and run (in reverse order) either when the returned disposer is called or when the fiber unloads, whichever comes first. Calling the disposer twice is a no-op.” — vendor/cordis/src/fiber.ts, ctx.effect()

The implementation is short enough to be the explanation: one effect's disposers are spliced out and walked in reverse, chained so an async teardown finishes before the next begins.

for (const disposable of disposables.splice(0).reverse()) {
  if (task) task = task.then(() => runDisposable(disposable))
  else { … }
}

Is it LIFO? Within one fiber, yes: the fiber's own list returns in reverse registration order — clear() in vendor/cordis/src/utils.ts ends with return values.reverse(), and the type doc says “Disposers run in reverse registration order when the owning fiber unloads”. But be precise about the shape, because it is not a single global stack:

  • Inside one effect, disposers run strictly one after another, in reverse order (the chained task.then(...) above).
  • Across one fiber's top-level effects, the list is handed out in reverse order but started concurrently: _unload() does await Promise.all(this._disposables.clear().map(async (dispose) => …)). Reverse order, overlapping execution.
  • Across fibers, a provider waits: “Dependents are notified when this fiber leaves ACTIVE, but may still access its services during their own teardown, so the effects of this fiber are only disposed after every dependent has unloaded” (fiber.ts, _unload()). The order among sibling dependents is not promised anywhere.

Dependency resolution is reactive, and activation and deactivation are one code path

A fiber computes a dependency “epoch” from the uid of each implementation it injected; when that string changes, the same function either reloads or unloads it:

_refresh() {
  let epoch = `${this._revision}`
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) { epoch = INACTIVE; break }
    epoch += ':' + impl.uid
  }
  this._setEpoch(epoch)
}

_setEpoch then runs _reload() when the fiber was inactive and can now be satisfied, and _unload() in the other direction. That is the coeffect mechanism in one function: “every context change is classified against a component's coeffect specification to drive its activation and deactivation.” The public form of the same idea is ctx.inject(deps, callback), whose doc says the callback “is unloaded and re-run whenever a required service changes”.

And a missing provider is not an error: the fiber sits in PENDING. The lifecycle enum is explicit about the states — PENDING — waiting for required services; LOADING — the callback is running; ACTIVE — loaded and providing; FAILED; UNLOADING — disposers are running; DISPOSED — the fiber was removed and cannot restart.

Every listener is an effect, which is why nothing has to be unsubscribed by hand

“The listener is removed automatically when the fiber unloads.” — vendor/cordis/src/events.ts, on()

The mechanism is one line: register() wraps the listener install in this.ctx.fiber.effect(() => { hooks.push(...); return () => this.unregister(name, callback) }, label). A plugin cannot install a listener and forget it, because the listener is owned by the fiber that installed it.

Timers get the same treatment only if you go through the framework's timer service. cordis-plugin-timer implements ctx.timeout as an effect that returns () => clearTimeout(timer), and ctx.interval likewise. A raw setInterval in plugin code is not captured by the kernel — see the table below.

The classic Node/JS plugin failureWhat Cordis actually does about itWhat it does not do
Lingering event listeners after a plugin is removedctx.on() is registered through ctx.fiber.effect() and returns the unregister call as its disposer; the fiber's teardown runs it.It does not track listeners registered outside a context — a module-level process.on is still yours to clean up.
Leaked singletons that outlive their ownerA Service registers itself in the constructor and “is automatically removed with the owning fiber”; the binding is a disposal, not a module-level variable.It does not stop a plugin from stashing a service in a module-scope variable; the object stays alive if you keep a reference.
Orphaned intervals/timeoutsctx.timeout() / ctx.interval() are effects whose disposer clears the timer, and a disposed pending ctx.timeout(delay) rejects rather than leaking.A bare setInterval is invisible to the kernel. “Use the timer service” is a convention the framework supports, not a sandbox it enforces.
Torn-down components still receiving workA provider's effects are disposed only after its dependents unload, and an INACTIVE_EFFECT error is thrown if a plugin tries to register on a dead context.In-flight async work is not cancelled for you; a plugin's own async body needs its own cancellation and its own disposer.

5. How dsh decomposes the agent runtime across that tree

The architecture doc says it twice, and both sentences are worth having in view while reading the table:

“Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so each is replaceable from configuration.” — docs/architecture.md:9

“There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads.” — docs/architecture.md:11

The policies are the part people assume is welded in. In dsh-base's patch the approval policy is a config field on a row — policy: (process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask' — and the presets are a table on another row. Changing the posture is changing a plugin's config, not editing the loop.

What that buys, stated by the architecture doc itself: “Seams are why one provider swap changes the whole product. Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks.”

The step, the turn, and the events between them

“A step is one model request plus the tools it calls. A turn is zero or more steps: it opens before its first input is claimed and closes once nothing is owed.” — docs/architecture.md

The flow, condensed to the durable and interceptable points:

turn/start
  claim next-step input + one queued message
  assemble prompt sections + step-admitted tool schemas
  → agent/pre-step            reject | enter(messages)
  step/start
  agent/request → prepareCall()
  llm/stream → assistant/message
  tool/call → tools/pre-execute → tools/execute → tools/post-execute → tool/result
  step/end
  another request owed, or input arrived → next step
  → agent/turn-stopping
turn/end

The events live in three domains, and the domain decides what a listener may do with the fact: session events are durable, appended to the log and broadcast through session/event; agent events (agent/*) carry a live Agent — inbox, step, status, request, validation, continuation — for work in flight; capability events (fs/*, tools/*, telemetry/*) attach policy and adapters to a seam without importing the loop.

Dispatch mode is part of that contract. agent/pre-step, agent/request, llm/stream and the three tools/* events are waterfalls, whose listeners must call next() to delegate; agent/turn-stopping is serial and has no next(). That is the difference between “you may veto or rewrite this” and “you may observe the decision that was made”.

Which makes the rejection semantics worth stating exactly: “agent/pre-step listeners accept, rewrite, or reject claimed messages; a rejected or empty first claim closes a durable turn without a step.” A turn that asks the model nothing is still a fact in the log — which is why the playground's rejection control grows the session while the step count stays at zero.

Above turns sits the goal. dsh-goal persists one objective across turns, resume, fork and restarts; dsh-goal-round-driver “automatically continues an active goal in the same session while the agent is idle… Each round gives the model another turn toward the objective”, bounded by a round cap that defaults to 256 and whose exhaustion records the blocker code round-limit. So goal ⊃ rounds ⊃ turns ⊃ steps is a real composition of four packages — not a hierarchy the docs draw as a diagram, and not one package nesting another.

6. Scopes and lifetimes: what actually gets its own context

This is the paragraph to check hardest, because the intuitive picture — every conversation, or every turn, is a child context with its own plugin lifetime — is not what the source does. There is no ctx.fork() anywhere in the vendored framework: a case-insensitive search for fork over vendor/cordis/src/ returns nothing. What Cordis gives you is three child-context constructors and one ownership rule.

  • ctx.extend(meta) — “Create a child context with extra metadata… The child prototypally inherits every property of this context… The parent is not mutated.”
  • ctx.isolate(name, label) — “Create a child context with an independent service scope for name… a different implementation can be provided without affecting the parent scope.”
  • ctx.intercept(name, config) — per-plugin config for plugins started below that context.
  • ctx.plugin(...) returns a fiber whose dispose() unwinds exactly that plugin's registrations and nothing else.

On top of that, dsh-scope mints a scoped registration context: createScope(ctx, key) calls ctx.plugin(scope), then returns fiber.ctx.extend({ [kScope]: key }), so everything registered through it is “both scope-visible and scope-lifetime”. The registries in the core group build on it: “a tool registered through agent.ctx is visible only to that agent”.

So the real lifetime model is:

EntityIs it a Cordis context?Lifetime
The applicationOne root Contextthe process
A pluginA fiber whose ctx is parent.extend({ fiber })mount → dispose; reload on config or code change
A profile / preset service overrideAn isolate() child contextas long as the profile or preset is composed
An agentYes — a scoped context minted per agent (createScope(loopCtx, this) in agent-loop/src/agent.ts), not a new rootctx.agents.create() / resume() → dispose(); the handle “stops the loop, unregisters, removes the session, unwinds the scope”

A subagentA separate agent, so a separate scope — and possibly a separate process or productits own session and handle; providers range from spawn-in-process to ACP/Codex/Claude Code

An earlier draft of this page — and the mental model behind a lot of writing about plugin harnesses — said a turn is a Cordis subcontext with its own plugin lifetime. The sources do not support that: a turn is a durable data structure inside one agent's lifetime, and the unit that gets an isolated registration context is the agent. The distinction matters when you design an extension: per-turn behaviour is an event listener on agent/*, not a plugin you mount for a turn.

dsh also ships the tree inspector that the last table describes: dsh-experimental-inspector publishes a CordisTreeSnapshot in which “every Fiber is a child of fiber.parent, owns exactly one Context child for fiber.ctx… Context-only extend(), isolate(), and intercept() layers remain direct Context descendants.” That is the tree this page's playground draws a small model of.

Part 2 — Malleable, user-customizable programs

7. The swap surface: what “reshapable” means here

A malleable program is one where the interesting decisions are configuration rather than code you cannot reach. dsh is a worked example, because each of these is a seam with a declared interface, one or more provider packages, and consumers that name only the interface:

The mechanism that makes a swap a user action is the patch layer: “A patch targets a row by id and replaces its whole config, or inserts new rows.” A profile's ordered bundles, its cordis.patch.yml, the home patch, then --patch overlays are applied to an empty entry list; dsh --profile web --dump-config prints the result, and “any row it prints can be replaced by a patch of your own.”

And the runtime version of the same idea is dsh-plugin-manager: “Enable or disable individual plugin entries, select installed bundles, and install or remove external bundles. With HMR enabled in YAML, configuration changes apply immediately; without HMR, the running composition remains until restart. Changes affect every session using the profile.”

8. Revertible effect trees, and what survives a swap

A user-installed behaviour is an effect like any other: it registers a listener, a prompt section, a tool, an adapter — each through ctx.effect() or ctx.on() — and unmounting takes them back in reverse order. That is the same machinery §4 quoted, so what it guarantees is exactly what §4 said and no more:

  • Guaranteed: every registration made through the context has an owner (the fiber), disposal is a single code path, a fiber's own registrations come off in reverse registration order, a provider's effects are disposed only after its dependents unload, and double disposal is a no-op.
  • Not guaranteed: that the heap is empty afterwards. “Zero leaks” is a property of the plugin's own diligence — timers through ctx.timer, listeners through ctx.on, no module-level caches — not a theorem the kernel enforces. A plugin that keeps a global reference, a bare setInterval, or an uncancelled promise leaks, and the framework will not notice.

Hot-swapping is where this becomes visible. The vendored HMR plugin (@deepseek-ai/cordis-plugin-hmr) “watches source files, traces Node's module graph, clears affected module caches, and reloads only the plugin entries that depend on changed application files”; dsh's own dsh-hmr is the same service under ctx.hmr with one coordinated queue for module changes, Include refreshes and profile configuration. Profile recompositions “also replace plugins whose loaded files below the profile directory changed on disk… therefore takes effect without a restart at the next such recomposition”, and a replacement that fails to load “stops the previous plugin and is reported as failed with its load error instead of as a restart” — a plugin does not half-load.

What survives a swap is the part of the program that lives in a different plugin. The session is the canonical case: “Model-visible means logged. Every model request must be reconstructable from the log”, and “Fork, resume, transcripts, telemetry, and persistence all derive from these durable settlements.” Swap the loop, swap the shell provider, swap the compaction strategy — the session log is owned by dsh-session and the transcript is derived from it, so the conversation does not move. What does not survive is anything the swapped plugin was holding in memory: in-flight async work, a queue built up inside the old loop, a cached summary that only existed as a field on the old instance. Those are re-derived or lost, and the honest design rule is to put anything that must outlive a swap into the log.

The restart boundary, from the docs rather than from optimism: HMR is config-only by default in dsh-base (config: { root: [] } — profile configuration reloads, module roots are opt-in), headless/SDK/ACP bundles disable it in YAML, and source watching requires root: ["."]. Installing packages runs outside HMR's queue, and the boot docs say some resolution changes still need one: “Installation mappings and local overrides still require a restart.” So: configuration and plugin code can be live; package installation and broken loads wait for a restart or a corrected file.

9. What a builder should copy

  1. Every registration returns a disposer, and the runtime holds it. Not a convention documented in a guide — a return type. If an API can add something, its return value should remove it, and the owner should be an object with a lifecycle (ctx.effect() here).
  2. Capabilities are seams with three roles. A definition, one or more providers, and consumers that name only the definition. A seam you cannot swap has not been designed; it has been named.
  3. Dependencies are declared, not sequenced. “Load order is expressed through service requirements rather than manual boot sequencing.” If your plugin system needs a boot order, it is a dependency graph drawn by hand.
  4. Activation and deactivation are the same code path. Compute an epoch from what a component needs; reload when it changes, unload when it does not hold. That is the whole coeffect mechanism, and it is ~20 lines.
  5. State that must outlive a swap lives in a log, not in the component. Event-sourced state is what makes hot-swapping safe rather than merely possible: the component can be replaced because it was never the owner of the record.
  6. Make the tree inspectable. dsh ships an inspector that exports the fiber tree as a snapshot; a plugin system whose composition cannot be printed is one you debug by restarting.

10. Playground: build and reshape a running program

No model is called. This is a deterministic model of the mechanics above: a plugin set, its registrations, a session log, a goal, and the seams — with every count computed from the controls by runtime.js and rendered by app.js. The panels are the claim: mount and unmount to watch registrations unwind, add or remove a provider to watch a dependent activate or deactivate, swap the shell seam, hot-swap the loop, run a turn, run a goal into its round cap, and mount a provider inside an isolated scope.

A. Mount and unmount plugins

The list is the composition, not a menu of features. Press a button to unmount an active plugin: its registrations come off the ledger one at a time, in reverse registration order, and any plugin that was waiting on a service it provided deactivates first. Press it again to mount it: it re-registers at the end of the ledger.

      C. The services on the root context

      Which plugin currently claims each ctx key. A key with no provider is not a crash: consumers that inject it go PENDING, which is dsh-tool-fs waiting for ctx.fs if you mount it before its provider.

      D. Hot-swap the agent loop, and swap the shell seam

      The loop is a plugin. Swapping its module unloads the current fiber — every registration unwinds — and mounts the new generation in the same context. The session log does not move: it belongs to dsh-session, which is not the plugin being swapped. The shell control swaps ctx.shell between dsh-bash-local and dsh-bash-sandbox; dsh-tool-bash is not edited, it loses the service, unloads, sees the new provider and reloads — which is why its three rows jump to the end of the ledger.

        E. An isolated scope

        ctx.isolate("shell") gives a subtree its own ctx.shell without touching the root's. Mount a sandbox provider inside that scope and unmount it again: the root ledger is identical before and after, which is what “scoped” has to mean to be worth anything. (There is no ctx.fork(); these three constructors and fiber ownership are the whole scoping API.)

            F. A step, a turn, and a rejection

            A step is one model request plus the tools it calls; a turn is zero or more steps, opened before its first input is claimed and closed once nothing is owed. Choose reject and run a turn: agent/pre-step refuses the claimed message and the turn closes durably with zero steps — the events are in the log, nothing was asked.

              G. A goal, its rounds, and the round cap

              dsh-goal persists one objective across turns; dsh-goal-round-driver continues it while the agent is idle, one round per turn, until the round allowance runs out. The shipped cap is 256 (defaultMaxGoalRounds); the control below sets a lower cap so you can watch it block. Exhaustion is not an error: it records the blocker code round-limit.

              What this does not model

              • Token counts. The per-tool schema sizes (bash 300, read 190, edit 220, write 200) are illustrative. The clone's schemas were not measured, and the page says so rather than dressing a guess as a measurement.
              • Concurrency. Cordis starts a fiber's top-level disposers in reverse order but concurrently (Promise.all). The animation is sequential, so it shows the order and not the overlap.
              • Sibling order. Cordis guarantees reverse order within a fiber and dependents-before-provider. The order among several dependents of one provider is not promised; the model picks one (reverse activation order) and this line is the disclosure.
              • Module loading. The hot swap is one modelled generation boundary. No file is watched, no module graph is traced, no cache is cleared; dsh-hmr does all three.
              • Config, loader and patches. The composition is a mounted set here, not a profile of ordered bundle rows, cordis.patch.yml layers and !!js expressions.
              • Real isolation. ctx.isolate is modelled for one service name; the real one can shadow any name, and isolation is a resolution scope, “not a sandbox or an authority boundary”.
              • Real work. No command runs, no tool executes, no model is called, no session is persisted. The session log is a list of typed strings, not SessionEvent payloads.
              • The event vocabulary. The turn flow shows the documented sequence, not every event: request/header, request/context, assistant/attempt, the tools/* pipeline stages inside one tool call and the internal/* events are all flattened or omitted.

              11. Limits and corrections

              A page like this is only useful if it says where it stops. These are the claims that are weaker than they look, and the ones an earlier version of this page got wrong.

              1. Correction: a turn is not a Cordis subcontext. Turns are durable records inside one long-lived agent; the isolated registration context belongs to the agent (§6). Design per-turn behaviour as an agent/* listener, not as a plugin mounted for a turn.
              2. Correction: there is no ctx.fork(). Cordis 4.1.0 as vendored exposes extend(), isolate() and intercept(). Scoping is a child context plus fiber ownership, and the playground's “isolated scope” control is that, not a fork.
              3. Correction: “spatiotemporal” is not about sandboxes or replay. It is the paper's two axes — revertible effects (time) and reactive coeffects (space) — and dsh's sandbox and session log are separate mechanisms (§2).
              4. Leak-freedom is a mechanism, not a guarantee. The kernel owns and unwinds what was registered through a context. Bare timers, module-level state and uncancelled promises are outside it (§4).
              5. HMR is not “everything is live”. dsh-base reloads configuration by default and watches module roots only when configured; headless, SDK and ACP disable it; package installs and some resolution changes need a restart (§8).
              6. The sandbox is file access. dsh-bash-sandbox's own summary: “network access and process visibility remain outside its guarantees”, and a command fails with SANDBOX_UNAVAILABLE rather than running unconfined. Do not read “sandboxed” as “contained”.
              7. The goal cap bounds continuation, not work. dsh-goal “stores goal state but does not schedule work”, and continuation permission is process-local rather than durable. Blocking with round-limit is a policy outcome, not a failure.
              8. The paper's formal claims are quoted from its abstract. Only the abstract page was reachable; theorem-level statements are not repeated here (§2).
              9. dsh is a developer preview. Its README promises compatibility-breaking changes, so every package name and file path here is pinned to commit fcc0ad4 rather than to a version.
              10. The playground is a model. It is deterministic and honest about its inputs, and it is not dsh: see what this does not model.
