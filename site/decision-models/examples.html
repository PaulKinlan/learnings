Examples

The report describes what these models do; these are the four call shapes you would actually write. Each one names what it sends and where, because the difference between a hosted request and a local one is the whole point.

Jev over HTTP

The hosted route. One POST carries the state, the questions and the options; the reply carries one answer object per question ID, never generated prose. [1]

curl https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $JEV_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "jev-1.13.0",
    "state": "The export fails in Safari; CSV export still works in Chrome.",
    "questions": {
      "severity": {
        "type": "score",
        "instructions": "How severe is the issue for the user?",
        "criteria": ["Cosmetic issue", "Degraded feature with workaround", "Blocking issue without workaround"]
      }
    }
  }'
Run this pattern in the lab

The reply is shaped {"answers":{"severity":{"type":"score","score":1.4,"probabilities":{…},"confidence":0.83}}}. core.js refuses a reply that adds an answer ID it did not ask for, or whose distribution does not sum to one: an extra answer fails the whole response rather than half-rendering it.

Jev from a page you serve yourself

A direct browser call from GitHub Pages is refused: the OPTIONS preflight to api.typesafe.ai with the Pages origin returned HTTP 400 and no Access-Control-Allow-Origin (measured 22 September 2026, no key used). Run npm run serve, open the loopback URL it prints, and the browser talks to your own origin instead.

// npm run serve prints a loopback URL. The relay forwards only /api/jev,
// /api/openai and /api/claude, checks same-origin, and logs nothing.
const key = document.querySelector('#decision-key').value; // memory only, never stored
const response = await fetch('/api/jev', {
  method: 'POST',
  credentials: 'omit',
  redirect: 'error',
  referrerPolicy: 'no-referrer',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${key}` },
  body: JSON.stringify({
    model: 'jev-1.13.0',
    state: 'The export fails in Safari; CSV export still works in Chrome.',
    questions: {
      severity: {
        type: 'score',
        instructions: 'How severe is the issue for the user?',
        criteria: ['Cosmetic issue', 'Degraded feature with workaround', 'Blocking issue without workaround'],
      },
    },
  }),
});
if (!response.ok) throw new Error(`Jev returned HTTP ${response.status}`);
const { answers } = await response.json();

Kev in this browser

The same decision, on your own machine, with no key and no server. The engine is the one this site runs: ONNX Runtime Web over a single packed sequence, with every artifact checked against a pinned SHA-256 before the runtime sees it.

import { loadKev } from './kev-engine.js';

// Nothing downloads until this call: a 7 MB tokenizer, a 1.3 MB graph and a
// 375 MB q4 weights file, once, from huggingface.co, cached after that.
const kev = await loadKev({
  onProgress: ({ stage, loaded, total }) => console.log(stage, loaded, total),
});

const { distributions, tokens, ms } = await kev.decidePacked(
  'The export fails in Safari; CSV export still works in Chrome.',
  [{
    instruction: 'How severe is the issue for the user?',
    options: ['Cosmetic issue', 'Degraded feature with workaround', 'Blocking issue without workaround'],
  }],
);

// One array of probabilities per question, in the order you asked them.
console.log(`${tokens} tokens in a single pass, ${ms.toFixed(0)} ms`, distributions[0]);
Run Kev in the playground

A graph that finds no delimiter tokens returns a flat distribution instead of raising. That is a failure speaking, not a confident tie, so compare the probabilities rather than reading the largest one.

Kev through its own local server

The same checkpoint behind an HTTP route, in the same request and response shape as Jev. Useful when you want one process to answer many clients.

git clone https://github.com/jaredpalmer/kev.git
cd kev
uv sync --extra serve
KEV_DTYPE=bf16 uv run --extra serve python -m kev.serve --run jaredpalmer/kev-0.8b --port 8009

# then, in another shell, the same body as the hosted request:
curl http://127.0.0.1:8009/v1/systemone \
  -H "Content-Type: application/json" \
  -d '{"model":"kev-0.8b","state":"The export fails in Safari.","questions":{"severity":{"type":"score","instructions":"How severe is the issue?","criteria":["Cosmetic","Workaround exists","Blocking"]}}}'
Run Kev in this tab instead

If you point a page at that server, the endpoint must be loopback only (localhost, 127.0.0.1 or [::1]) and the path must be exactly /v1/systemone — core.js refuses anything else, including a URL that carries credentials, a query string or a fragment. Upstream laya-serve answers the same shape but binds 0.0.0.0 with no authentication unless LAYA_API_KEY is set: do not expose it on a network you do not control.

Schema playground

A specification is plain data: title, description, state, and questions keyed by lowercase IDs. Each question is one of three types, and the limits are enforced, not suggested:

  • noul — one probability of yes, optional criteria with exactly true and false descriptions.
  • choice — 2 to 255 named options, each with a description. The model selects one; it cannot invent an option.
  • score — 2 to 10 ordered levels. The answer is an expected level, which may be fractional.

Any other field is refused. No code, no URLs, no extra UI: the renderer is fixed, so a schema can describe a decision but never an application. Checking here is the same walker the lab and the generator use, so a schema this page accepts is one they accept.
