How it runs: five backends

For matrices A[M, K] and B[K, N], the product C[i, j] = ∑ₖ A[i, k]B[k, j] is mathematically invariant. But execution time varies by orders of magnitude across runtimes. What changes is where arrays live, who schedules threads, how memory moves through cache lines, and the boundary crossing overhead between host and accelerator.

The universal execution cost model

Every runtime evaluated in this series—from single-threaded JavaScript to a thousand-core GPU—obeys the same fundamental execution time bound:

t≈tlaunch+bytes movedβ+FLOPsP

Each term represents an independent physical constraint on the system:

  • tlaunch: the fixed latency to invoke the kernel. On CPU this is a function call (nanoseconds); on GPU it includes command buffer encoding, queue submission, and pipeline dispatch (hundreds of microseconds).
  • β: effective memory bandwidth. Memory operations are bounded by how fast bytes move into registers from L1 cache (terabytes/sec), DRAM (tens of gigabytes/sec), or PCIe buses (gigabytes/sec).
  • P: peak arithmetic throughput (floating-point operations per second). Once data is in registers, execution is bounded by the number of arithmetic logic units (ALUs) and clock frequency.

Which term dominates depends on the arithmetic intensity I=FLOPs/byte and tensor dimensions:

When I<P/β, the ALUs spend cycles stalled waiting for cache fills. When I>P/β, the memory bus is idle while ALUs operate at peak saturation.

The crossover point: when WebGPU beats CPU JavaScript

A common mistake is assuming GPU acceleration is automatically faster for every operation. For small tensors, host-to-device command submission and asynchronous readback dominate the execution time.

For a square n×n matrix multiply, the computation requires 2n3 FLOPs and transfers 3·4n2=12n2 bytes. Consider representative parameters on a modern laptop:

  • JavaScript CPU peak: PCPU≈50 GFLOP/s (single core, scalar/JIT vectorization), tlaunch≈0.
  • WebGPU peak: PGPU≈2 000 GFLOP/s (integrated/discrete GPU), with a fixed round-trip launch and mapping overhead tlaunch+map≈0.8 ms.

The crossover size n* occurs where execution times are identical:

tJS=2n3PCPU,tGPU=tlaunch+map+2n3PGPU 2n3(1PCPU−1PGPU)=tlaunch+map⇒n3≈0.8×10−32(2×10−11−5×10−13)≈2.05×107 n*≈2.05×1073≈274

Below n≈274 (matrix size 274 × 274), plain JavaScript is faster than WebGPU because the GPU sits idle while the CPU spends 0.8 ms encoding command buffers and awaiting mapAsync(). Past n=512, WebGPU pulls ahead by an order of magnitude, because n3 arithmetic completely amortizes the fixed launch penalty.

Benchmarking correctness checklist

Benchmarking cross-backend code requires guarding against runtime-specific optimization artifacts. Every rule below prevents a specific measurement error:

PracticeWhat it preventsFailure mode if omitted
Kernel warmup iterationsMeasuring JIT compilation or shader pipeline creationFirst call includes 50–200 ms of Shaderc/Dxc compilation, reporting 1 000× slower performance than steady-state.
Asynchronous fence / synchronizationMeasuring command submission instead of executionStopping the timer before mapAsync() or torch.cuda.synchronize() resolves measures only the 0.05 ms queue push, falsely reporting infinite throughput.
Isolate memory transfer from computeConflating bus bandwidth with arithmetic capacityA GPU kernel running in 0.1 ms preceded by a 2 ms PCIe buffer upload is reported as slow, misdiagnosing compute rather than data locality.
Pre-allocate input and output buffersMeasuring memory allocator locks and GC pausesAllocating fresh Float32Array or torch.zeros in a loop measures garbage collection latency rather than GEMM arithmetic.
Assert numerical error tolerancesMeasuring kernels that produce corrupted or zero outputA broken shader or loop that exits prematurely runs in 0 µs, appearing as the "fastest" implementation while producing garbage.
Verify cache residency assumptionsMeasuring cold DRAM fetches instead of cache throughputTesting a 64 KiB matrix immediately after a cold allocation measures DRAM row misses rather than steady-state L1/L2 bandwidth.
