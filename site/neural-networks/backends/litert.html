LiteRT on phones and the edge

LiteRT, the runtime that grew out of TensorFlow Lite, runs a converted model from a .tflite FlatBuffer, hands the operators it can to a CPU, GPU or NPU delegate, and usually stores weights and activations as int8. This chapter derives the int8 arithmetic, prints the quantizer that runs in the playground in full, and draws the delegate split and the file layout.

Run it first

The playground quantizes six numbers, [−1, −0.1, 0, 0.1, 1, outlier], to int8 and decodes them again with quantizeAffineInt8 from math.js. Move the slider from 4 to 100 and watch −0.1, 0 and 0.1 merge into one integer. The rest of the page explains that collapse and what deployed models do about it. Everything here runs in JavaScript; the page does not load a LiteRT runtime or call a phone delegate.

Affine int8, derived from the range

int8 has 256 codes, −128 to 127. A real tensor has a range [min, max]. Affine quantization maps that range linearly onto the codes: one real step s (the scale) per integer step, and one integer z (the zero point) that stands for real 0. The range is first widened to include 0, so min ≤ 0 ≤ max. Spreading max − min over the 255 gaps between 256 codes gives the scale, and requiring min to land on −128 gives the zero point:

s=max−min255,z=round(−128−mins) q=clamp(round(xs)+z,−128,127),x^=(q−z)s

Real 0 encodes as round(0) + z = z and decodes as (z − z)·s = 0, exactly. That is why z is rounded to an integer instead of being left fractional: zero padding in a convolution and every zero that a ReLU emits must survive the round trip without error.

The error bound

Write r = round(x/s). Rounding to the nearest integer moves a number by at most one half, so |x/s − r| ≤ ½. If the clamp does not fire, q − z = r and

|x−x^|=|x−rs|=s·|xs−r|≤s2

The clamp does not fire for any x in [min, max]. JavaScript’s Math.round(y) is ⌊y + ½⌋, so round(n + y) = n + round(y) for any integer n. At the bottom of the range, q(min) = round(min/s) − 128 − round(min/s) = −128. At the top, max/s = min/s + 255, so q(max) = −128 + 255 = 127. Rounding is monotone, so everything between lands between. The clamp is there for floating point: (max − min)/255 is itself rounded, and max/s can come out a hair above min/s + 255. C’s round, which TFLite’s reference code uses, rounds halves away from zero and is not shift-invariant for negative ties, so there the clamp can matter in exact arithmetic too.

The literal 0 in lines 2 and 3 widens the range to include zero, which the exact-zero argument above needs. For [0.5, 0.9] the range becomes [0, 0.9] and the codes below the data are wasted. Spreading ...values passes every element as a function argument: with 100 000 elements it works in Node 24, with 200 000 it throws RangeError: Maximum call stack size exceeded. Production code reduces with a loop. One NaN makes min and max NaN. || 1 catches a zero scale (an all-zero tensor) and, because NaN is also falsy, replaces a NaN scale with 1 instead of reporting it; line 6 still yields a NaN zero point, and every output is NaN.

This is z = round(−128 − min/s) with the integer −128 moved outside the rounding, which the shift identity above allows. min ≤ 0, so −min/s ≥ 0 and z ≥ −128. An all-positive tensor gets z = −128; [−1, 1] gets z = −1, because min/s = −127.5 and Math.round takes that half up to −127.

The encode step, q = clamp(round(x/s) + z, −128, 127). The array is a plain JavaScript Array of numbers, not an Int8Array; nothing here stores bytes.

Decode is x̂ = (q − z)·s, and maxError is the largest |x − x̂|, the number the playground reports. By the proof above it never exceeds scale / 2 by more than floating-point rounding. An empty input gives Math.max() = −Infinity.

One outlier, worked in numbers

These are the playground’s values at its default slider position and at the far end, as quantizeAffineInt8 returns them. The test that checks the listings above also checks that these integer rows are what the function produces.

Every value decodes to within s/2 ≈ 0.0098. The worst error is 0.00196 on ±0.1, which sits 0.1 of a step from the nearest code. The interval [−1, 1] covers 103 codes, −128 to −26.

Now −0.1, 0 and 0.1 all give |x/s| = 0.2525 or less, all round to 0, and all encode as the zero point −125. They decode to exactly 0.0. Any value with |x| < s/2 = 0.198 is erased, whatever its sign. ±1 rounds to ±3 steps and decodes as ±1.1882, an 18.8% error, still inside the bound s/2. The whole interval [−1, 1] now spans 7 of the 256 codes, −128 to −122; the other 249 codes are spent on the gap between 1 and 100 that holds a single value. The scale is set by the range, and the range is set by the largest magnitude, so one entry decides the resolution of every other entry in the tensor.

In a weight matrix this is a real failure. Many weights are small, and when they all decode to 0 the layer loses the features they carried. Accuracy measured after conversion drops, and the reason is the step size, which can be computed from max and min before running anything.

Smaller scale groups: per-channel, group-wise, outlier-preserving

The fix is to stop sharing one scale across values that have different ranges. Suppose the outlier sits in a different output channel from the other five values. Give each channel its own scale and the five small values are quantized against their own range:

schemevaluesscaleint8max |x − x̂|
per-tensor affine[−1, −0.1, 0, 0.1, 1, 100]0.396078−128, −125, −125, −125, −122, 1270.188235
per-tensor symmetric[−1, −0.1, 0, 0.1, 1, 100]0.787402−1, 0, 0, 0, 1, 1270.212598
per-channel affine[−1, −0.1, 0, 0.1, 1]0.007843−128, −14, −1, 12, 1270.003922
per-channel symmetric[−1, −0.1, 0, 0.1, 1]0.007874−127, −13, 0, 13, 1270.002362

Per-channel scales cost one float per output channel, and they fit the integer GEMM below only along the output axis. For C = AB with weights B[K, N], a scale sB,j per output column j sits outside the sum over k and becomes a per-column multiplier:

Cij=sAsB,j∑k=0K−1(qA,ik−zA)qB,kj

A scale per activation channel would be indexed by k and stay inside the sum, so the sum would no longer be a plain integer dot product. That is why the TFLite int8 specification quantizes weights per channel and symmetrically (z = 0, codes −127 to 127) and quantizes activations per tensor and affinely.

Group-wise scaling cuts the reduction axis into groups of g elements (commonly 32 or 128) with one scale per group and column. Each group’s integer dot product is computed separately, multiplied by its scale and accumulated in float, so there is one extra multiply per g MACs. Storage overhead is one fp16 scale per g weights, 16/g bits per weight: int4 with g = 128 costs 4.125 bits per weight. An outlier now damages only its own group.

Outlier-preserving schemes handle activations, where per-channel scales do not fit. LLM.int8() (Dettmers et al., 2022) finds the few activation feature dimensions with magnitude above a threshold (6.0 in the paper), multiplies those columns and the matching weight rows in fp16, and runs everything else in int8. SmoothQuant (Xiao et al., 2022) instead rescales each input channel k by a factor that divides the activation and multiplies the weight row, leaving the product unchanged, and folds the division into the preceding layer offline:

Y=(Xdiag(σ)−1)(diag(σ)W),σk=max|X:,k|αmax|Wk,:|1−α

With α = 0.5, the paper’s main setting, channel k of the scaled activations and row k of the scaled weights both end up with maximum magnitude √(max|X:,k|·max|Wk,:|): the outlier is split evenly between the two quantizers instead of landing entirely on the activations.

quantizeSymmetricInt8, line by line

The symmetric variant used for weights, also from math.js, in three listings.

The range is [−maxAbs, maxAbs], with no zero point to fit. Dividing by 127, not 127.5 or 128, keeps the code range symmetric, −127 to 127: if q is a code then −q is too, so negating a weight never overflows. Code −128 goes unused. A tensor that is all non-negative, such as a ReLU output, uses only codes 0 to 127 and wastes one bit of resolution, which is why activations stay affine.

z = 0, so encode is round(x/s). |x/s| ≤ 127 by construction, so this clamp also only catches floating-point slop. Math.round(-0.127) returns −0, which shows up as -0 in the array and decodes to −0 = 0.

Decode is q·s. Every rounding error is again at most s/2, with s = maxAbs/127. Returning zeroPoint: 0 keeps the result shape identical to the affine function, so callers can treat both alike.

Why int8 GEMM is fast

Substitute A ≈ sA(qA − zA) and B ≈ sB(qB − zB) into one output element of C = AB and expand the product inside the sum:

∑k(qA,ik−zA)(qB,kj−zB)=∑kqA,ikqB,kj⏟hot loop−zB∑kqA,ik−zA∑kqB,kj+KzAzB

Only the first term costs M·N·K multiplies, and it multiplies raw codes: int8 × int8, accumulated in int32. The other three are corrections. Σk qA,ik is one sum per row of A, M·K adds per inference. Σk qB,kj is one sum per column of the weights, which are constant, so the converter or the kernel’s prepare step computes it once. K·zA·zB is one constant. With symmetric weights zB = 0 and the row-sum term disappears; the remaining −zA·colsumj is a per-column constant folded into the int32 bias. The hot loop is then a pure integer dot product.

int32 does not overflow in practice. One product is at most 128 × 128 = 214 in magnitude (127 × 127 with symmetric weights), so K products fit while K·214 ≤ 231 − 1, that is K ≤ 131 071, far above any layer width.

CPUs and GPUs have one instruction for four of these products into one int32 lane. Arm’s SDOT (Armv8.2-A dot-product extension) on 128-bit registers:

SDOT Vd.4S, Vn.16B, Vm.16B           one instruction, 16 int8 MACs

lane              0                    1                    2                    3
Vn  int8  │ a0  a1  a2  a3     │ a4  a5  a6  a7     │ a8  a9  a10 a11    │ a12 a13 a14 a15    │
Vm  int8  │ b0  b1  b2  b3     │ b4  b5  b6  b7     │ b8  b9  b10 b11    │ b12 b13 b14 b15    │
          │      4 products    │      4 products    │      4 products    │      4 products    │
Vd  int32 │ d0 += a0b0+…+a3b3  │ d1 += a4b4+…+a7b7  │ d2 += a8b8+…       │ d3 += a12b12+…     │

FMLA Vd.4S, Vn.4S, Vm.4S              one instruction, 4 f32 MACs

Same register width, four times the multiply-accumulates. x86 has VPDPBUSD (AVX-VNNI and AVX-512 VNNI), the same operation on 256 or 512 bits, but it multiplies unsigned × signed bytes. Kernels store activations as uint8 by adding 128 to every code, which adds 128 to zA; the correction terms above absorb the change unaltered. NVIDIA GPUs have DP4A: four int8 products plus an int32 add, per thread, per instruction. The second gain is bandwidth: an int8 weight is one byte against four for f32, so a GEMV at batch size 1, which is limited by how fast it streams weights, reads a quarter of the bytes.

Requantization with a fixed-point multiplier

The int32 accumulator holds C/(sAsB) (after the corrections and bias). The next layer wants int8 codes at the output’s scale sC and zero point zC:

qC=clamp(zC+round(M·acc),−128,127),M=sAsBsC=2−nM0,M0∈[0.5,1)

M is a real number known at conversion time, usually well below 1. Gemmlowp and TFLite (following Jacob et al., 2018) avoid floating point here by storing M0 as a Q31 integer, round(M0·231), and n as a shift. At run time: a 32 × 32 → 64-bit multiply, keep the rounded high 32 bits (Arm’s SQRDMULH does this in one instruction), then a rounding right shift by n.

Worked: sA = 0.02, sB = 0.005, sC = 0.05 give M = 0.002 = 2−9 × 1.024. 1.024 is not below 1, so n = 8 and M0 = 0.002 × 256 = 0.512, stored as round(0.512 × 231) = 1 099 511 628. For acc = 12 345: 12 345 × 1 099 511 628 = 13 573 471 047 660; adding 230 and shifting right by 31 gives 6 321; adding 27 and shifting right by 8 gives 25. The float reference is round(12 345 × 0.002) = round(24.69) = 25. Then add zC and clamp. A fused ReLU is the same clamp with the lower limit raised from −128 to zC, the code for real 0, so it costs nothing extra.

How a delegate splits the graph

When the app attaches a delegate, LiteRT’s interpreter calls the delegate’s prepare function with the whole graph. The delegate inspects each node’s operator code and parameters, returns the indices of the nodes it can run, and the interpreter groups each connected run of supported nodes into one partition. Each partition is replaced by a single delegate kernel node (TfLiteContext::ReplaceNodeSubsetsWithDelegateKernels in the C API). Everything else stays on the CPU path. One unsupported op in the middle of a chain makes three partitions:

model graph                         delegate says
  input
  CONV_2D                 ✓  ┐
  DEPTHWISE_CONV_2D       ✓  ├─ partition 1 → one NPU delegate kernel
  CONV_2D                 ✓  ┘
  CUSTOM "my_op"          ✗  ── stays on the CPU (built-in or custom kernel)
  CONV_2D                 ✓  ┐
  MEAN                    ✓  ├─ partition 2 → one NPU delegate kernel
  FULLY_CONNECTED         ✓  ┘
  output

after partitioning:
  input → [NPU kernel 1] ⇄ copy/sync → my_op (CPU) ⇄ copy/sync → [NPU kernel 2] → output

The graph is a chain, so nothing overlaps. While the CPU runs my_op, the NPU has no work; while partition 2 runs, the CPU waits:

time ─────────────────────────────────────────────────────────────────────────▶
NPU  │███ partition 1 ███···································███ partition 2 ███│
bus  │                   ▒ sync+copy ▒         ▒ sync+copy ▒                   │
CPU  │································█ my_op █································│
                         └──────── NPU idle (bubble) ──────┘

Each crossing costs a synchronization (the CPU must wait until the accelerator has finished and its writes are visible) plus moving the tensor. On a phone with unified memory the move is often a cache flush and a layout conversion instead of a DRAM-to-DRAM copy, because GPU and NPU delegates keep tensors in their own internal layouts, but it is still serial work on the critical path. The cost model:

t≈∑partitionstp+∑crossings(tsync+bytescβ)

With illustrative round numbers, not measurements: a 56 × 56 × 64 int8 activation is 200 704 bytes, about 20 µs at 10 GB/s. If a crossing’s synchronization and dispatch cost 100 µs, two crossings add 240 µs before my_op does any work. For a model whose delegated partitions take 1–2 ms in total, that adds 12–24%. The fixes follow from the diagram: rewrite my_op at conversion time as operators the delegate supports, implement it inside the delegate, or move it to the start or end of the graph so there is one crossing instead of two. The interpreter logs how many nodes each delegate claimed and into how many partitions; more than one partition means at least one round trip.

The .tflite file: a FlatBuffer read in place

A .tflite model is a FlatBuffer: one contiguous byte array in which every reference is a 32-bit offset relative to where it is stored, never a pointer. Nothing has to be fixed up after loading, so the runtime can mmap the file read-only and read fields directly from the mapped pages. There is no parse pass and no allocation per field.

.tflite file, mmap'd read-only                      all offsets are little-endian
byte 0  ┌──────────────────────────┐
        │ u32 root offset ─────────┼───────────────┐  root table at 0 + value
byte 4  │ "TFL3" file identifier   │               │
        ├──────────────────────────┤               │
   V    │ vtable of Model          │◀──────┐       │
        │ u16 vtable size          │       │       │
        │ u16 table size           │       │       │
        │ u16 field 0  version     │       │       │
        │ u16 field 1  op_codes    │       │       │
        │ u16 field 2  subgraphs   │       │       │
        │ u16 field 3  description │       │       │  0 = absent: use the default
        │ u16 field 4  buffers     │       │       │
        ├──────────────────────────┤       │       │
   T    │ Model table              │◀──────┼───────┘
        │ i32 soffset: T − V ──────┼───────┘          signed, so V can sit after T
        │ u32 version = 3          │
        │ u32 uoffset ─────────────┼──▶ vector<OperatorCode>
        │ u32 uoffset ─────────────┼──▶ vector<SubGraph>
        │ u32 uoffset ─────────────┼──▶ vector<Buffer>: u32 length, then length uoffsets
        └──────────────────────────┘

Reading field f of the table at T: load the i32 at T to find the vtable at V = T − soffset; if f’s slot in the vtable is inside the vtable size and nonzero, the field is at T + slot; if the field is a table, vector or string, add the u32 stored there to its own address. A few loads and adds. Fields missing from the vtable read as their schema default, which keeps files small and lets the schema append fields without breaking older readers. The schema (schema.fbs) defines the tree that those offsets encode:

Model
├─ operator_codes  [CONV_2D, FULLY_CONNECTED, CUSTOM "my_op", …]
├─ subgraphs[0]
│  ├─ tensors[12]  name "conv1/filter"
│  │               shape [64, 3, 3, 32]   type INT8   buffer 7
│  │               quantization  scale[64], zero_point[64] = 0, quantized_dimension 0
│  ├─ operators[0] opcode_index 0, inputs [0, 12, 13], outputs [14]
│  └─ inputs [0]   outputs [41]
└─ buffers
   ├─ [0]  empty: by convention, the buffer of every tensor without constant data
   └─ [7]  data: 18 432 bytes = 64·3·3·32 int8 weights, read in place

The per-channel weight scales from earlier live in the tensor’s quantization table: 64 scales for 64 output channels, zero points all 0, and quantized_dimension naming the axis they index. A tensor refers to its data by buffer index, so the CPU kernel’s weight pointer can point straight into the mapped file; the converter aligns buffer data to 16 bytes so the pointer is usable for SIMD loads.

Two limits. 32-bit offsets cap a FlatBuffer at 2 GiB, so newer schema versions add 64-bit offset and size fields to Buffer that point at weight data appended after the FlatBuffer itself. And zero-copy ends where a delegate wants another layout: XNNPACK repacks weights into its own blocked format when it prepares the graph, which allocates a second copy and costs start-up time; LiteRT can cache the packed weights on disk to skip the repack on later loads.
