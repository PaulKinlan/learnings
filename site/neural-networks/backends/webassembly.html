WebAssembly and SIMD

Execute a compiled scalar f32 GEMM kernel and inspect how it shares linear memory.

Pointers are byte offsets

WebAssembly exports a linear memory. This kernel copies A and B into non-overlapping regions, passes byte offsets and dimensions to gemm_f32, and copies C back to a Float32Array. The JavaScript view uses float indices, so the offsets passed to WASM multiply those indices by four.

The module is generated from checked-in bytes without a network download or toolchain. The page permits only WebAssembly compilation through the CSP’s wasm-unsafe-eval directive, not arbitrary JavaScript evaluation. A runtime refusal is shown rather than labelled as a successful WASM run.

Enable JavaScript to use this local playground. The explanation and sources below work without it.

What SIMD changes — and what this demo does not

The demo uses scalar f32 instructions. WASM SIMD adds 128-bit vectors, allowing four f32 lanes per instruction. A vectorized multiply-accumulate loop needs suitable contiguous loads, tail handling when dimensions are not multiples of four, and a layout that avoids excessive shuffling. SIMD is not automatic merely because code runs in WASM.

Threads require shared memory, appropriate browser isolation headers and explicit synchronization. This single-threaded demo does not claim multicore or SIMD speedups. Its byte generator is printed in full under the Multiply button.
