WebAssembly and SIMD

Execute a compiled scalar f32 GEMM kernel and inspect how it shares linear memory. The module is 208 bytes written out by hand in buildWasmGemmBytes(); this chapter prints the generator, every one of those bytes, and the instruction each byte encodes.

Run it first

The button copies A = [1, 2; 3, 4] and B = [5, 6; 7, 8] into the module’s memory, calls the exported gemm_f32, and copies C back. The expected product is [19, 22; 43, 50]. The module is built from bytes in engine.js, with no download and no toolchain. The page’s Content Security Policy allows WebAssembly compilation through 'wasm-unsafe-eval' and nothing else of the eval family. If compilation is refused, the widget reports that instead of printing a JavaScript result under a WebAssembly label.

Enable JavaScript to use this local playground. The explanation and listings below work without it.

The module, byte by byte

A WebAssembly binary is a fixed 8-byte preamble followed by sections. Each section is one id byte, its payload length as an unsigned LEB128 number, then the payload. A decoder that does not care about a section can skip it using the length alone. These are the first 58 bytes of the module that runs above, each row an offset, the bytes, and their meaning. A test checks that the rows on this page, concatenated, equal the output of buildWasmGemmBytes().

The magic number is the four bytes \0asm; the version is the 32-bit integer 1, stored little-endian like every multi-byte fixed value in WebAssembly.

Section 1 declares function signatures. 0x60 introduces a function type, then a vector of parameter types and a vector of result types, each prefixed by its count. 0x7f is i32, 0x7d is f32, 0x7b is v128. The signature is (i32 i32 i32 i32 i32 i32) → (): aPtr, bPtr, cPtr, M, K, N. Section 3 lists, for each function defined in the module, the index of its type; the bodies come much later. The split lets a compiler validate every call against its callee’s signature before it has seen any body, which is what makes streaming, parallel compilation possible. Section 5 declares one memory with flags 0 (minimum only, no maximum) and a minimum of 16 pages. A page is 64 KiB, so the memory starts at 1 MiB.

Section 7 exports two things by name. Names are a length byte followed by UTF-8. The kind byte says what is exported: 0 a function, 2 a memory. JavaScript sees them as instance.exports.memory, a WebAssembly.Memory, and instance.exports.gemm_f32, a function. There is no import section: the module creates its own memory instead of receiving one.

Section 10 holds the function bodies, one here. Its length, 153, and the body’s length, 150, are the only values in the module too large for a single LEB128 byte. Section ids must appear in increasing order (1, 3, 5, 7, 10 here); a decoder rejects them otherwise.

LEB128

Unsigned LEB128 writes an integer seven bits at a time, least significant group first. Each byte carries seven payload bits; its top bit is 1 if another byte follows and 0 on the last byte. Small numbers, which dominate (counts, indices, sizes), take one byte, and no length has a fixed upper limit. The standard worked example is 624 485:

624 485 = 0x98765 = 0b 0100110 0001110 1100101
                        group 2  group 1  group 0
emit group 0 + continue: 1 1100101 = 0xe5
emit group 1 + continue: 1 0001110 = 0x8e
emit group 2, last:      0 0100110 = 0x26
bytes: e5 8e 26     decode: 0x65 + 0x0e·2⁷ + 0x26·2¹⁴ = 624 485
153=25+1·27→(25|0x80),1=99 01,150=22+1·27→96 01

The generator encodes those two values with this helper from engine.js. It is not exported, so the test compares this listing against the text of engine.js itself:

n & 0x7f takes the low seven bits, n >>>= 7 drops them (an unsigned shift, so the loop ends for any non-negative 32-bit input), and byte |= 0x80 sets the continuation bit when more bits remain. Instruction immediates such as i32.const use the signed variant, which sign-extends from the last byte’s bit 6. That is why i32.const -4 in the SIMD listing below is the single byte 7c.

The generator, in full

buildWasmGemmBytes() is 72 lines: a byte array for the function body, then the module around it. Seven consecutive listings, nothing omitted.

The body opens with its local declarations, in run-length form: 2 groups, 3 locals of i32 (7f), 1 local of f32 (7d). Parameters are locals 0–5, so these become locals 6, 7, 8 (i, j, k) and 9 (sum). Locals start at zero.

The two outer loops. Each is a block wrapped around a loop; the 0x40 after each opcode is the empty block type, meaning the construct takes and leaves nothing on the stack.

0x43 is f32.const followed by four raw IEEE 754 bytes, little-endian; all zero is 0.0. Each iteration of j resets the accumulator before the k loop opens.

The innermost loop is a dot product over k: i, j, k order, the same order the JavaScript chapter measured as slow, because it reads B with a stride of N floats.

Six 0x0b bytes close the six blocks and loops, and a seventh closes the function. The indentation of the source mirrors the nesting; the bytes carry none of it.

The fixed sections are literal bytes, decoded row by row in the hex table above.

The code section is assembled last because its length prefix depends on the body length. codeSectionPayload is the function count, the body size and the body; the section size wraps all of that.

The code section as instructions

WebAssembly is a stack machine. Each instruction pops its operands from an implicit operand stack and pushes its result; the validator checks every function’s stack types before it runs, so the engine can compile the stack away into registers. Here is the 150-byte body, each opcode next to its text-format (WAT) name. Names after $ are added for reading; the binary only has indices. Every byte is shown, and the test decodes each row’s first opcode and checks the name.

The local declarations, i = 0, and the head of the i loop. br_if pops an i32 and branches if it is non-zero. Its immediate is a label depth counted outwards from the innermost enclosing construct: 0 is $loop_i, 1 is $break_i. Branching to a loop jumps back to its start; branching to a block jumps past its end. So br_if 1 is “break” and br 0 is “continue”. i32.ge_u compares unsigned: a negative dimension passed from JavaScript reads as a number above 2 billion.

The j loop starts the same way, then sets sum to the f32 constant whose four little-endian bytes are 00 00 00 00, sets k to 0 and opens the k loop.

The first operand of the eventual add, sum, is pushed early and waits on the stack. Then the address of A[i, k]: aPtr + ((i·K + k) << 2). The shift by 2 multiplies the float index by 4, turning it into a byte address. f32.load carries a memarg: an alignment hint as a power of two (2 means 4 bytes) and a constant offset added to the address (0 here). The hint never changes the result; a misaligned access is only possibly slower.

Same for B[k, j]: bPtr + ((k·N + j) << 2). Then f32.mul pops the two loaded floats and pushes their product, f32.add adds it to the waiting sum, and local.set stores the new sum.

After the k loop ends, the store address C[i, j] is computed first and the value second, because f32.store pops the value from the top and the address beneath it.

Why it disagrees with the JavaScript kernel in the last bit

Byte 0x97 is f32.mul: the product is rounded to binary32 before byte 0x98, f32.add, rounds again. jsMatmul computes the product exactly in binary64 and rounds only the sum. Same inputs, same order of k, different rounding points. Over 2 000 random 16-term dot products with entries in (−1, 1) the two kernels disagreed in 1 150, each by one unit in the last place; for example −2.0644471645355225 (JavaScript) against −2.0644474029541016 (WebAssembly), 2−22 apart. Neither is wrong. They are two legitimate binary32 kernels, which is why cross-backend tests compare with a tolerance.

The k loop executes 33 instructions per multiply-add: 18 compute the two addresses, 9 are loop control, and 6 do the work (push sum, two loads, multiply, add, store sum). An engine compiles them to far fewer machine instructions, but the shape is fixed: one scalar multiply-add per iteration.

Linear memory

A WebAssembly memory is one contiguous, zero-initialised byte array, addressed from 0. In JavaScript it is memory.buffer, an ordinary ArrayBuffer. Typed-array views over that buffer and the module’s loads and stores touch the same bytes, which is the whole interface: JavaScript writes inputs through a view, calls the export with addresses, and reads outputs through a view. getWasmBackend() lays the three matrices end to end:

byte 0             4MK               4MK+4KN            4MK+4KN+4MN      1 MiB
     ┌──────────────┬─────────────────┬──────────────────┬───────────────┐
     │ A  (M·K f32) │  B  (K·N f32)   │  C  (M·N f32)    │    unused     │
     └──────────────┴─────────────────┴──────────────────┴───────────────┘
f32  0              M·K               M·K + K·N          (float index)
2×2 demo: A = bytes 0–15, B = 16–31, C = 32–47

Five listings of getWasmBackend(), nothing omitted:

new WebAssembly.Module(bytes) validates and compiles synchronously, and new WebAssembly.Instance instantiates; both are fine for 208 bytes. Large modules should use WebAssembly.compileStreaming or instantiate, which compile off the main thread. The instance is cached, so the compile happens once per page.

Lines 13–17 grow the memory when the three matrices do not fit. The initial 1 MiB holds square matrices up to:

3·n2·4≤16·65 536⇒n≤295

memory.grow(pages) adds whole 64 KiB pages and can only grow, never shrink. With no maximum declared, the ceiling is the engine’s limit for 32-bit memories, at most 65 536 pages (4 GiB); past it grow throws a RangeError.

Line 18 creates the view after the grow, and this order is essential. Growing a memory detaches its old ArrayBuffer: memory.buffer becomes a new, larger buffer, and every view over the old one becomes length 0. Lines 19–21 compute offsets in floats, because that is what the view indexes. Line 24 passes byte addresses to gemm_f32, because WebAssembly loads and stores take byte addresses; hence the * 4 on each. Line 25 copies C out, so the caller’s result does not alias memory the next call will overwrite.

The classic bug is to hoist the view to save an allocation:

// WRONG: the view is created once, before any grow.
const f32 = new Float32Array(memory.buffer);
function matmul(A, B, M, K, N) {
  if (neededBytes > memory.buffer.byteLength) memory.grow(extraPages);
  f32.set(A, 0);   // after a grow: TypeError, detached ArrayBuffer
  …
}

In Node 24, set on the stale view throws TypeError: Cannot perform %TypedArray%.prototype.set on a detached ArrayBuffer. Plain element access is worse: f32[0] reads undefined and f32[0] = 5 is silently dropped. The fix is the one line 18 already uses: re-create the view after any call that might grow, or compare view.buffer !== memory.buffer.

If compilation throws, for example under a CSP without 'wasm-unsafe-eval', the backend reports available: false and quietly substitutes jsMatmul. The widget on this page checks available first and refuses to label a JavaScript result as WebAssembly.

Memory is also where WebAssembly’s safety comes from. Every load and store is checked against the memory’s current size; an out-of-range address traps, which JavaScript sees as a WebAssembly.RuntimeError. The module cannot reach the JavaScript heap at all. gemm_f32 itself never checks M, K and N against the memory, so the grow on lines 13–17 is what keeps its addresses in range.

SIMD: four lanes per instruction

The fixed-width SIMD extension adds one value type, v128, and instructions that treat it as lanes: f32x4 sees four binary32 values. v128.load reads 16 bytes, f32x4.mul and f32x4.add work lane by lane, v128.store writes 16 bytes. Each lane rounds exactly as the scalar f32.mul and f32.add would, so a correct vector loop gives bit-identical results to the scalar one in the same order.

The kernel above cannot be vectorized as it stands. Its inner loop is over k, and consecutive B[k, j] values are 4N bytes apart, not adjacent. Reorder to i, k, j, as jsMatmul already is, and the inner loop becomes C[i, j..] += A[i, k]·B[k, j..] over contiguous j: an axpy, which is exactly the shape SIMD wants. The function below is not part of engine.js and the demo above does not run it. It is (func $axpy (param $cPtr i32) (param $bPtr i32) (param $a f32) (param $n i32)), and a test in tests/nn-chapters-links.test.js assembles these exact bytes into a module, validates it, and checks the output against a scalar Math.fround reference for every n from 0 to 13.

Set-up. SIMD opcodes share the prefix byte fd followed by a LEB128 sub-opcode, so f32x4.mul (sub-opcode 230) is fd e6 01. f32x4.splat copies a into all four lanes once, outside the loop. n & ~3 is n rounded down to a multiple of 4: the part the vector loop can cover.

The vector loop. Each pass handles C[j..j+3]: load four floats of C and four of B, multiply B by the splatted a, add, store four floats back, and advance j by 4. The memarg on the 16-byte loads and stores is 02 00, an alignment hint of 4 bytes, not 16: a row of B or C starts at a multiple of 4 bytes only, and claiming 16 would be a lie the engine is entitled to punish with a slow path.

The scalar tail handles the last n mod 4 elements with the same instructions as the scalar kernel. Without it, any row length not divisible by 4 would leave up to three columns unwritten; with n = 10 the vector loop covers j = 0…7 and the tail j = 8, 9.

Count instructions. Both loop bodies, including the bounds test and the branch, are 30 instructions per pass. The scalar loop makes one pass per element, the vector loop one per four:

Iscalar=30N,ISIMD=30⌊N4⌋+30(Nmod4),N=256:7 680→1 920

Four times fewer WebAssembly instructions per element. That is not a measured fourfold speed-up. These are WebAssembly instructions, not machine instructions; 24 of the 30 in each body are address arithmetic and loop control, which an engine compiles to far less; and once B streams from beyond L2, memory bandwidth limits both loops the same way. A tuned kernel bumps pointers instead of recomputing j << 2, keeps several accumulators in v128 registers across k, and blocks for cache. The relaxed-SIMD extension adds f32x4.relaxed_madd, which may fuse the multiply and add into one rounding on some hardware and not on others; it is faster where it fuses, at the cost of results that are no longer bit-identical across machines.

Threads

A WebAssembly memory declared shared is backed by a SharedArrayBuffer, so several workers can instantiate the same module over the same bytes and each compute a band of rows of C. Browsers expose SharedArrayBuffer only to cross-origin-isolated pages, served with Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp (or credentialless), because a second thread incrementing a shared counter is a high-resolution timer, the ingredient of Spectre-style side-channel attacks. The threads extension adds atomic loads, stores and read-modify-writes, plus memory.atomic.wait32 and memory.atomic.notify, which let a worker sleep until another wakes it instead of spinning. The main thread is not allowed to block that way. This page is single-threaded and makes no multicore claim.
