WebAssembly and SIMD

Execute a compiled scalar f32 GEMM kernel and inspect how it shares linear memory. Rather than opaque binary hex dumps, WebAssembly provides a clean, human-readable text format (WAT). This chapter inspects the complete WAT implementation, stack-machine instructions, memory growth traps, and an optimized 128-bit SIMD vector loop.

The module is synthesized in engine.js using buildWasmGemmBytes() and compiled synchronously in the browser via new WebAssembly.Module().

How structured control flow works

WebAssembly has no arbitrary goto instruction. Control flow is structured into nested block and loop labels:

  • Branching to a loop (e.g. (br $loop_k)) jumps to the beginning of the loop (a backward loop continue).
  • Branching to a block (e.g. (br_if $break_k ...)) jumps to the end of the block (a forward loop break).

Memory addresses are calculated in bytes. Because each float32 is 4 bytes wide, the element index (i·K+k) is shifted left by 2 bits (i32.shl ... 2) before adding the base pointer $aPtr. Loads (f32.load) and stores (f32.store) operate directly on linear memory.

The in-browser byte generator

In engine.js, buildWasmGemmBytes() writes out the exact 208 binary bytes corresponding to the WAT module above. The complete function is printed below in seven consecutive listings with zero omission:

Locals 0–5 are the six function parameters; locals 6–8 are loop counters i, j, k (i32); local 9 is the running accumulator sum (f32).

Each loop header uses opcode 0x02 (block) wrapped around 0x03 (loop), with 0x40 specifying the empty block type (no stack return value).

Opcode 0x43 is f32.const followed by 4 raw IEEE 754 little-endian bytes (00 00 00 00 for 0.0). Local 9 (sum) is reset at the start of each column.

The reduction body: loads float from A, loads float from B, multiplies via 0x94 (f32.mul), adds to sum via 0x92 (f32.add), and branches backward to $loop_k via 0x0c 0x00.

Store result to C with opcode 0x38 (f32.store) and close all outer blocks with 0x0b (end).

Section headers declare the binary magic number (\0asm), version (1), and Type Section (declaring the 6-parameter signature).

Section sizes and function lengths that exceed 127 bytes are encoded using uleb128():

Linear memory and the detached view trap

WebAssembly exports a linear memory: an array of 64 KiB pages addressed from 0. In JavaScript, this memory is exposed via memory.buffer as an ArrayBuffer. getWasmBackend() partitions memory linearly across matrices A, B, and C:

byte: 0               4·M·K              4·(M·K + K·N)       4·(M·K + K·N + M·N)    1 MiB
      ┌──────────────────┬──────────────────┬───────────────────┬──────────────────────┐
      │  A (M·K float32) │  B (K·N float32) │  C (M·N float32)  │  free memory         │
      └──────────────────┴──────────────────┴───────────────────┴──────────────────────┘
float:0                  M·K                M·K + K·N           M·K + K·N + M·N

The host driver in engine.js manages initialization, memory sizing, and execution:

The instance is compiled once synchronously from bytes and cached in memory.

The initial 16 pages (1 MiB) accommodate square matrices up to 3·4n2≤1 048 576⇒n≤295. When matrix dimensions exceed 1 MiB, memory.grow() adds 64 KiB pages.

The detached view trap

Notice that line 18 allocates the Float32Array view after memory.grow(). Hoisting the view outside to avoid per-call allocation introduces a critical failure mode:

// WRONG: creating the view once before a potential memory.grow() call
const f32 = new Float32Array(memory.buffer);
function matmul(A, B, M, K, N) {
  if (needed > memory.buffer.byteLength) memory.grow(extraPages);
  f32.set(A, 0); // Throws TypeError: Cannot perform %TypedArray%.prototype.set on a detached ArrayBuffer
}

Whenever WebAssembly linear memory grows, the engine detaches the old ArrayBuffer and allocates a new, larger buffer elsewhere in the process address space. Any existing Float32Array view pointing to the old buffer is instantly detached with byte length 0. Attempting to call .set() throws a TypeError, while property reads return undefined. Line 18 rebinds the view to the current memory.buffer on every call.

128-bit SIMD vectorization in WAT

WebAssembly fixed-width SIMD adds the v128 value type (16 bytes). In f32x4 mode, a single vector register holds four 32-bit floating-point numbers. Vectorizing our GEMM requires reordering the loops from i,j,k to i,k,j, turning the inner loop into an AXPY kernel (C[j…j+3]+=a·B[j…j+3]):

Instruction count comparison

Both the vector loop and scalar tail loop require 30 WebAssembly instructions per pass. But the vector loop processes 4 elements per pass:

Iscalar=30N,ISIMD=30⌊N4⌋+30(Nmod4)

For N=256, the scalar loop executes 7 680 instructions, while the SIMD loop executes only 1 920 instructions—a 4× instruction reduction.

Threads and SharedArrayBuffer

Multi-threaded WebAssembly requires declaring a shared memory backed by a SharedArrayBuffer. Browsers restrict SharedArrayBuffer to cross-origin isolated environments (requiring Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp) because concurrent thread counter increments can be exploited as high-resolution timers for Spectre-style cache timing attacks. The WebAssembly threads proposal introduces atomic instructions (i32.atomic.rmw.add, memory.atomic.wait32, memory.atomic.notify) to coordinate worker threads without busy-waiting.
