WebGPU compute shaders

This chapter reads one 57-line WGSL matrix-multiply shader and the 52-line JavaScript function that runs it, both copied verbatim from engine.js. Every hardware claim below is tied to a specific line.

Run it first

The button multiplies A = [1, 2; 3, 4] by B = [5, 6; 7, 8] on your GPU. The expected product is [19, 22; 43, 50]. If the browser exposes no navigator.gpu, or requestAdapter() returns null (common in headless browsers, virtual machines and blocklisted drivers), the widget says so and stops. It never prints a CPU result labelled as GPU output. The shader that runs is printed in full under the button.

Enable JavaScript to use this local playground. The explanation and listings below work without it.

How a GPU runs one function many thousand times

You write a compute shader from the point of view of one invocation: one row index, one column index, one output cell. dispatchWorkgroups(x, y, z) launches that function x·y·z times per workgroup, and the GPU does not schedule those invocations one by one. It packs them into fixed-width groups that share a single instruction stream. WGSL calls such a group a subgroup. NVIDIA calls it a warp and uses 32 lanes. AMD calls it a wavefront, with 64 lanes on GCN and 32 or 64 on RDNA. Apple GPUs use 32. Intel GPUs compile to 8, 16 or 32 lanes depending on the shader.

A subgroup fetches one instruction and executes it in every active lane, each lane holding its own registers. That model is SIMT: single instruction, multiple threads. Each lane looks like a thread with its own program counter, but the lanes in a subgroup advance together. An 8 × 8 workgroup (64 invocations) occupies two 32-wide NVIDIA warps or one 64-wide AMD wavefront. WGSL does not tell you the subgroup width or which invocations share a subgroup, so the shader cannot rely on lockstep execution for correctness. Explicit barriers carry that guarantee, as the barrier section shows.

Divergence

When lanes in one subgroup take different sides of an if, the hardware cannot run both sides at once. It runs the then side with the disagreeing lanes masked off, then runs the else side with the first group masked off. The subgroup pays for both paths. A loop costs as many iterations as its slowest lane needs. The only data-dependent branches in this shader are bounds checks (lines 33, 39 and 54 of the listing). Every lane in an interior workgroup takes the same side. Only workgroups that overhang a matrix edge diverge, and each side of those branches is a single store, which compilers often lower to a branchless select.

Latency hiding

A load from device memory takes hundreds of cycles. A CPU core hides that latency with large caches and out-of-order execution. A GPU compute unit keeps many subgroups resident and, when one stalls on a load, issues instructions from another that is ready. How many subgroups fit at once (occupancy) is bounded by the register file and by on-chip workgroup memory, both divided among the resident workgroups. That makes register count and workgroup memory size performance parameters, not only correctness parameters.

Where the data lives, and why bandwidth is the limit

WGSL exposes the memory hierarchy as address spaces. var<storage> buffers live in device memory: GDDR or HBM on a discrete card, shared system DRAM on integrated GPUs and Apple silicon. Every invocation in every workgroup can read it, and the bandwidth is hundreds of GB/s shared by the whole chip. var<workgroup> variables live in on-chip SRAM, called shared memory on NVIDIA and LDS (local data share) on AMD. Only the invocations of one workgroup can see it, it lasts only as long as that workgroup, and it is an order of magnitude faster to reach. WebGPU guarantees at least 16 384 bytes of workgroup storage per workgroup by default (maxComputeWorkgroupStorageSize). This shader uses 512 of them: two 8 × 8 tiles of 4-byte floats.

Arithmetic intensity of the naive kernel

Count the work for C[M×N] = A[M×K]·B[K×N]. Each output needs K multiply-adds, or 2K floating-point operations. In the naive kernel each invocation reads its whole row of A and its whole column of B straight from device memory, so it issues 2K four-byte loads:

FLOPs=2MNK,loadsnaive=2MNK,Inaive=2MNK4·2MNK=14 FLOP/byte

I is arithmetic intensity: floating-point operations performed per byte moved from device memory. The count assumes no cache reuse, which is the worst case; real L1/L2 caches will catch some repeats, but the kernel gives the hardware no structure to exploit.

The roofline model turns intensity into a speed limit. A kernel can go no faster than the chip’s peak arithmetic rate, and no faster than the rate at which memory can feed it:

attainable FLOP/s=min(Ppeak,I·β)

Take an illustrative mid-range discrete GPU with P = 20 TFLOP/s of f32 and β = 500 GB/s of memory bandwidth. These are round numbers for the arithmetic, not a measurement of any product. The ridge point, where the two limits meet, is P/β = 40 FLOP/byte. At I = 0.25 the naive kernel is capped at 0.25 × 500 GB/s = 125 GFLOP/s, about 0.6% of peak. The arithmetic units spend more than 99% of their cycles waiting for operands. The kernel is memory-bound, and no amount of faster arithmetic changes that.

Tiling divides the traffic by B

Tiling uses the fact that every element of A is needed by N different outputs, and every element of B by M outputs. A workgroup that computes a B × B block of C loads a B × B tile of A and a B × B tile of B into workgroup memory once per step along K. All B² invocations then read those values from on-chip memory instead of fetching them again from device memory. There are (M/B)(N/B) workgroups, each runs K/B steps, and each step loads 2B² floats:

loadstiled=MB·NB·KB·2B2=2MNKB,Itiled=B4 FLOP/byte

With B = 8, as in this shader, intensity rises eightfold to 2 FLOP/byte and the cap on the illustrative GPU rises to 1 TFLOP/s, 5% of peak. That is a large improvement and still memory-bound. Reaching the 40 FLOP/byte ridge would need B ≈ 160, and with one invocation per output cell, B is capped far below that. WebGPU’s default maxComputeInvocationsPerWorkgroup is 256, so B ≤ 16 and I ≤ 4 FLOP/byte for this design. Kernels that actually become compute-bound give each invocation a block of outputs held in registers. With 256 invocations each accumulating an 8 × 8 block, a workgroup covers a 128 × 128 tile of C, I reaches 128/4 = 32 FLOP/byte, and the illustrative cap rises to 16 TFLOP/s, 80% of peak. The section on what this kernel leaves on the table returns to that design.

Tiling geometry

Take M = K = N = 16 with B = 8. The dispatch is dispatchWorkgroups(ceil(N/8), ceil(M/8), 1) = 2 × 2 workgroups. Workgroup (wx, wy) owns the 8 × 8 block of C whose rows start at 8·wy and whose columns start at 8·wx. It walks along K in numTiles = ceil(K/8) = 2 steps:

            K →                       N →
        ┌───────┬───────┐         ┌───────┬───────┐
        │ A0,0  │ A0,1  │       K │▓B0,0▓▓│ B0,1  │
   M    ├───────┼───────┤       ↓ ├───────┼───────┤
   ↓    │▓A1,0▓▓│▓A1,1▓▓│         │▓B1,0▓▓│ B1,1  │
        └───────┴───────┘         └───────┴───────┘
          t = 0   t = 1          ▓ = column block 0

                N →
            ┌───────┬───────┐
          M │ C0,0  │ C0,1  │   workgroup (wx=0, wy=1)
          ↓ ├───────┼───────┤   computes C1,0:
            │▓C1,0▓▓│ C1,1  │   t=0: += A1,0 · B0,0
            └───────┴───────┘   t=1: += A1,1 · B1,0

Inside the workgroup, invocation (lx, ly) with lx, ly ∈ [0, 8) owns one output cell and loads one element of each tile per step:

row=8wy+ly,col=8wx+lx,tileAly,lx←Arow,8t+lx,tileBly,lx←B8t+ly,col

The 64 invocations together fill both tiles with 128 device-memory loads. After the barrier, each invocation reads a row of tileA and a column of tileB, 16 on-chip reads for 8 multiply-adds:

          tileA (8×8)                  tileB (8×8)
        ┌─────────────────┐          ┌─────────────────┐
        │ · · · · · · · · │          │ · · · · · ▓ · · │
        │ · · · · · · · · │          │ · · · · · ▓ · · │
  ly=2 →│ ▓ ▓ ▓ ▓ ▓ ▓ ▓ ▓ │          │ · · · · · ▓ · · │
        │ · · · · · · · · │          │ · · · · · ▓ · · │
        │ · · · · · · · · │          │ · · · · · ▓ · · │
        │ · · · · · · · · │          │ · · · · · ▓ · · │
        │ · · · · · · · · │          │ · · · · · ▓ · · │
        │ · · · · · · · · │          │ · · · · · ▓ · · │
        └─────────────────┘          └─────────────────┘
                                                 ↑ lx=5
   acc += tileA[2][k] * tileB[k][5]   for k = 0 … 7

Without the tiles, the same 64 invocations would issue 64 × 16 = 1 024 device loads for that step, eight times as many.

Coalescing

The shader maps global_id.x to the column, so neighbouring lanes (consecutive lx) read neighbouring addresses. In A[row * K + aCol] the eight lanes of one row of the workgroup read eight consecutive floats, 32 contiguous bytes. In B[bRow * N + col] they also read 32 contiguous bytes. The memory system can serve each group of eight lanes with one wide transaction instead of eight separate ones; NVIDIA hardware, for instance, moves device memory in 32-byte sectors. If the shader mapped x to the row instead, each of those loads would stride by K or N floats and touch a different sector.

Bank conflicts

Workgroup memory is usually split into 32 banks, each 4 bytes wide, and each bank serves one address per cycle. Lanes reading different addresses in the same bank are serialised; lanes reading the same address get a broadcast. In the inner loop, tileA[lRow][k] is the same address for all eight lanes in a row, so it broadcasts. tileB[k][lCol] is eight consecutive floats in eight different banks. Neither read conflicts.

Ragged edges

When M, K or N is not a multiple of 8, the last workgroups overhang the matrix. Lines 33–43 store 0.0 into tile slots that fall outside A or B, so the inner loop on line 47 can always run exactly 8 iterations. A padded column of A (aCol ≥ K) always meets a padded row of B (bRow ≥ K) at the same k, so the extra products are 0 × 0 and leave acc unchanged. The 2 × 2 demo above is the extreme case: ceil(2/8) = 1 workgroup of 64 invocations, of which 4 compute a real output and 60 multiply zeros and then skip the store on line 54.

Barriers: execution order and memory visibility

workgroupBarrier() provides two guarantees. For execution, no invocation in the workgroup passes the barrier until every invocation in the workgroup has reached it. For memory, every write to var<workgroup> memory made before the barrier is visible to every read after it. The execution guarantee alone would not be enough, because a write can sit in a store buffer or a non-coherent cache after its instruction has retired; the memory half is what makes another invocation’s value readable. The barrier covers only the workgroup address space. storageBarrier() gives the same ordering for storage buffers, and only within one workgroup. Nothing in WGSL makes one workgroup wait for another inside a dispatch. To consume results from other workgroups, end the dispatch and start another; WebGPU orders the two dispatches’ storage accesses for you.

The loop needs two barriers per step, for two different hazards:

step t:  store tileA/tileB  (each lane writes 1 slot of each)
         ─── barrier #1 (line 45) ── read-after-write ───
         8 × acc += tileA[ly][k] * tileB[k][lx]
         ─── barrier #2 (line 51) ── write-after-read ───
step t+1: store tileA/tileB (overwrites the same 128 slots)

Barrier #1 closes a read-after-write hazard. Each invocation’s inner loop reads 16 tile slots, and 15 of them hold values written by other invocations: 7 others in its row of tileA and 8 others in its column of tileB. Without the barrier, a lane could read a slot before its owner has written it and accumulate a stale value or zero.

Barrier #2 closes a write-after-read hazard. Without it, a subgroup that finishes its 8 multiply-adds first would loop back to line 33 and overwrite tileA and tileB with step t+1 data while a slower subgroup is still reading step t. On a 64-wide AMD wavefront the whole 8 × 8 workgroup is one subgroup, so this race may never show up in testing. On 32-wide hardware the workgroup is two subgroups and the race is real. Since NVIDIA Volta, even lanes within one warp are not guaranteed to stay in lockstep. The barrier makes the shader correct on all of them.

Why out-of-range invocations must not return early

The obvious way to handle the overhang is to stop invocations that have no output cell. It is wrong:

// WRONG: do not write this.
if (row >= dims.M || col >= dims.N) { return; }
for (var t = 0u; t < numTiles; t++) {
  …
  workgroupBarrier();   // waits for 64 invocations; some have left
}

The invocations that returned never reach the barrier. On hardware that counts arrivals, the rest of the workgroup can wait forever; and the returned invocations never load their share of the tiles, so even if the GPU did not hang, the surviving invocations would read garbage. CUDA makes __syncthreads() in divergent code undefined behaviour and leaves you to find the hang. WGSL rejects it at compile time instead. Its uniformity analysis requires every workgroupBarrier() to be reached in uniform control flow, meaning all invocations of the workgroup must take the same path to it. row comes from global_invocation_id, so it is non-uniform, and a return that depends on it makes everything after it non-uniform. createShaderModule does not throw for this; the error appears in getCompilationInfo() and as a validation error on the device.

The real shader keeps all 64 invocations in the loop and moves the bounds test to two places where it is legal. Lines 33–43 turn out-of-range loads into zero stores, and line 54 guards the final store, which comes after the last barrier. The loop itself is legal because its trip count, numTiles, depends only on dims.K from a uniform buffer, which is the same value for every invocation. Change the loop bound to anything derived from row or col and the shader stops compiling.

The shader, line by line

This is WGSL_GEMM_SHADER from engine.js, split into eight consecutive listings with nothing omitted. Line numbers count from the first line of the shader string. A test in tests/nn-chapters-links.test.js fails if these listings ever stop matching the source.

The host passes the three matrix sizes as data instead of compiling them into the shader, so one pipeline serves every shape. u32 is a 32-bit unsigned integer. _pad makes the struct 16 bytes, exactly the Uint32Array([M, K, N, 0]) that the host writes into the uniform buffer. The shader never reads it.

@group(0) is the index passed to setBindGroup(0, …) on the host. @binding(n) matches { binding: n } in createBindGroup. var<uniform> is a small read-only buffer, the same value for every invocation; that sameness is what makes dims.K uniform for the barrier rule above. var<storage, read> and var<storage, read_write> are device-memory buffers. C needs read_write because the shader stores into it. array<f32> without a length is a runtime-sized array whose length comes from the bound buffer’s size. An out-of-bounds index cannot corrupt other memory: WGSL defines such an access to stay inside the binding (implementations clamp the index or discard the access), which is part of why WebGPU can run untrusted shaders. All three matrices are row-major, so A[i,k] lives at index i·K + k.

var<workgroup> declares one copy per workgroup, shared by its 64 invocations and placed in on-chip memory. array<array<f32, 8>, 8> is an 8 × 8 array in row-major order: tileA[r][c] is float number 8r + c. Two tiles × 64 floats × 4 bytes = 512 bytes. WGSL zero-initialises workgroup memory when the workgroup starts, but this shader writes every slot before reading it.

@compute marks main as a compute entry point; its name must equal entryPoint: "main" in createComputePipeline. @workgroup_size(8, 8, 1) fixes 64 invocations per workgroup at compile time, under the default limit of 256 total and 256 in x and y. @builtin(local_invocation_id) is the invocation’s coordinate inside its workgroup, each component in [0, 8) here. @builtin(global_invocation_id) is workgroup_id * workgroup_size + local_invocation_id, computed per component: its coordinate across the whole dispatch.

x is the column and y the row; that choice is what makes the loads coalesce. acc is a function-scope variable, so it lives in a register, private to the invocation. (dims.K + 7u) / 8u is ceiling division in integers: K = 2 gives 1 tile, K = 8 gives 1, K = 9 gives 2.

Line 29 walks along K one tile at a time. Lines 30–31: this invocation fetches column t·8 + lCol of row row in A, and row t·8 + lRow of column col in B. Lines 33–43 are the cooperative load: each of the 64 invocations performs one global load per tile, or one zero store if its element lies outside the matrix. These are the only device-memory reads in the shader.

Line 45 is barrier #1 (read-after-write). Lines 47–49 are the arithmetic: 8 multiply-adds, reading 8 floats from tileA and 8 from tileB, two on-chip loads per multiply-add. That ratio is the next bottleneck once device memory is solved; register tiling cuts it. Line 51 is barrier #2 (write-after-read). Both barriers sit inside a loop whose trip count is uniform.

The bounds test on line 54 is legal here because no barrier follows it. Invocations outside C skip the store; the rest write their accumulated dot product to device memory. This is the shader’s only device-memory write, one per output cell.

The host: from adapter to pipeline

The shader does nothing until JavaScript compiles it and hands it to a queue. initWebGPUBackend() does the one-time work; it is printed here in full in six listings.

The result is cached only on success. A failed probe sets checked but leaves available false, so the next call probes again instead of remembering the failure for ever.

navigator.gpu exists only in a secure context (HTTPS or localhost) in a browser with WebGPU enabled. Node has a navigator global but no gpu property, so under npm test this branch is taken every time.

requestAdapter() chooses a physical GPU and driver. It resolves to null instead of rejecting when none is suitable, so the code tests the result. This call passes no powerPreference, so the browser picks.

requestDevice() with no descriptor gives a logical device with no optional features and the default limits, not the adapter’s maximums. A shader that needed more than 16 384 bytes of workgroup memory would have to request a higher maxComputeWorkgroupStorageSize here. A device can also be lost later, through a driver reset or a GPU process crash; device.lost is a promise that resolves when that happens. This engine does not listen to it, so after a loss webgpuState keeps a dead device.

createShaderModule parses and validates WGSL, and it does not throw on a WGSL error. Errors come back through shaderModule.getCompilationInfo() and as a validation error on the device. layout: "auto" derives the bind group layout from the shader’s @group/@binding declarations. createComputePipeline also returns synchronously; given an invalid module it returns an invalid pipeline and reports the error asynchronously. The try/catch around this code therefore catches a rejected requestDevice(), but not a shader that failed to compile. createComputePipelineAsync() would reject with a GPUPipelineError in that case. This is the step where the browser translates WGSL into the platform’s shading language (HLSL for D3D12, MSL for Metal, SPIR-V for Vulkan) and the driver compiles that to machine code, which is why it is done once and cached.

The device and pipeline are kept for every later multiply.

The host: one dispatch, start to finish

webgpuMatmulAsync(A, B, M, K, N) runs once per multiply. Nine listings, nothing omitted.

If WebGPU is unavailable this function silently returns the WebAssembly result. That is convenient for a library and misleading in a lesson, so the widget above calls initWebGPUBackend() first and refuses to run when available is false.

GPUBufferUsage is a bit mask, and the numbers on line 7 are its values. The uniform buffer is UNIFORM | COPY_DST: it is bound as a uniform and is the destination of writeBuffer. queue.writeBuffer copies the bytes out of dimsData when it is called, so the array could be reused at once, and the GPU is guaranteed to see the data before any work submitted later on the same queue.

Math.max(16, …) keeps every buffer non-empty so the bindings are valid even when a dimension is zero. A and B are STORAGE | COPY_DST: bound as storage and filled by writeBuffer. C is STORAGE | COPY_SRC: the shader writes it and a copy reads it. The read-back buffer is MAP_READ | COPY_DST. WebGPU allows MAP_READ only together with COPY_DST, so the shader cannot write a mappable buffer directly. The design reflects the hardware: on a discrete card, C lives in VRAM, and the mappable buffer lives in memory the CPU can reach across PCIe. The explicit copy is the transfer.

The input matrices go up the same way as the dimensions. Like every writeBuffer, these are ordered before the submit on line 41.

A bind group fills the slots the shader declared. getBindGroupLayout(0) fetches the layout that "auto" derived for @group(0); each binding number matches the @binding on lines 8–11 of the shader. Buffer types must match too: binding a MAP_READ buffer at binding 3 would be a validation error.

A command encoder records commands; nothing executes yet. dispatchWorkgroups(x, y, 1) launches x × y workgroups of 64 invocations each. x = ceil(N/8) covers the columns and y = ceil(M/8) the rows, matching the x-is-column mapping in the shader. Each dimension is limited to 65 535 workgroups by default. For the 2 × 2 demo this is one workgroup.

copyBufferToBuffer is recorded outside the compute pass because copies are not allowed inside one. Its size, M·N·4 bytes, must be a multiple of 4. encoder.finish() seals a command buffer and queue.submit hands it to the GPU. submit returns immediately; the GPU has not necessarily started.

mapAsync(1) is GPUMapMode.READ. The promise resolves only after all submitted work that uses readBuf has finished, so this await is the only point where JavaScript waits for the GPU. getMappedRange returns an ArrayBuffer that views the mapped memory. unmap() detaches that ArrayBuffer and sets its length to zero, which is why line 44 copies the data out with .slice() before line 45 runs.

destroy() releases GPU memory now instead of whenever the garbage collector finds the JavaScript wrapper. The function allocates five buffers and a bind group on every call. That is fine for a demonstration and wasteful in a training loop, where the buffers would be created once and reused.

The two sides run on separate timelines:

JavaScript (content timeline)      GPU (queue timeline)
─────────────────────────────      ───────────────────────────
writeBuffer(u, A, B)  ──────────▶  staged uploads
createBindGroup, encode
queue.submit([cmd])   ──────────▶  upload u, A, B
await mapAsync(READ)                dispatch 1×1 workgroups
   (event loop keeps running)       copy C → readBuf
                       ◀──────────  work done; map completes
getMappedRange().slice()
unmap(); destroy()

For the 2 × 2 demo the GPU performs 8 multiply-adds. Against that, the host creates five buffers and a bind group, makes three uploads, one submission and one map round trip. The demo checks correctness; it says nothing about speed. A GPU starts to win once the matrices are large enough that 2MNK FLOPs dwarf the fixed cost of a submit and a readback, and the readback disappears entirely when the next operation consumes C on the GPU, as successive layers of a network do.

What this kernel leaves on the table

The shader is correct and readable, and it is far from fast. The changes a production kernel makes, in roughly the order they pay off:

  • Register tiling. Give each invocation a T × T block of outputs. Per step along k it loads T values of A and T of B from workgroup memory and performs T² multiply-adds, so on-chip loads per multiply-add fall from 2 to 2/T. Combined with larger workgroup tiles this raises device-memory intensity as computed above, from 2 FLOP/byte to tens.
  • Wider loads. Reading vec4<f32> moves 16 bytes per instruction instead of 4, cutting load instruction count by four.
  • Lower precision. The optional shader-f16 feature halves bytes per element, which doubles arithmetic intensity on its own.
  • Subgroup operations. The optional subgroups feature lets lanes exchange registers directly, skipping a round trip through workgroup memory.
  • Host reuse. Allocate buffers and bind groups once, keep intermediate results on the GPU between layers, and read back only what JavaScript needs.
  • Error handling. Listen to device.lost, check getCompilationInfo(), and prefer createComputePipelineAsync() so a failed compile becomes a rejected promise.
