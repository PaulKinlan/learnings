JavaScript and typed arrays

Inspect and run a matrix product using contiguous Float32Array storage. The 15-line function that runs is jsMatmul from engine.js, printed below in full; every performance claim is tied to one of its lines or to a measurement whose conditions are stated.

Run it first

The button multiplies A = [1, 2; 3, 4] by B = [5, 6; 7, 8] with jsMatmul. The expected product is [19, 22; 43, 50]. The source printed under the button comes from Function.prototype.toString at run time, so it is the code that executes.

Row-major storage and 64-byte cache lines

A Float32Array is a view over one contiguous ArrayBuffer: element n occupies bytes 4n to 4n + 3. A matrix has no shape of its own in that buffer. The code decides that an M × K matrix is stored row after row (row-major), so element A[i, k] sits at index i·K + k:

A (M = 2, K = 3)         Float32Array A, flat
┌──────┬──────┬──────┐   index:  0     1     2     3     4     5
│ A0,0 │ A0,1 │ A0,2 │         ┌─────┬─────┬─────┬─────┬─────┬─────┐
├──────┼──────┼──────┤         │ A0,0│ A0,1│ A0,2│ A1,0│ A1,1│ A1,2│
│ A1,0 │ A1,1 │ A1,2 │         └─────┴─────┴─────┴─────┴─────┴─────┘
└──────┴──────┴──────┘   byte:   0     4     8    12    16    20
                         A[i,k] → index i·3 + k → byte 4(i·3 + k)
A[i,k]↦index iK+k,byte 4(iK+k),cache line ⌊iK+k16⌋

Assumes the buffer starts on a 64-byte boundary. Large ArrayBuffer backing stores usually do, but nothing in the language promises it; a misaligned start shifts every line boundary by the same amount and changes none of the counts below.

The CPU never fetches one float. It moves memory between DRAM and its caches in fixed blocks called cache lines, 64 bytes on current x86 and Arm cores. One line holds 16 consecutive float32 values. The first read of any of them pays for the whole line; the other 15 are then nearly free while the line stays in the L1 data cache. The machine used for the measurements on this page (AMD Ryzen 9 9955HX) has a 48 KiB, 12-way L1d per core: 768 lines in 64 sets of 12.

Loop order decides the stride

C = A·B needs, for every i, j and k, the product A[i,k]·B[k,j] added into C[i,j]. The three loops can nest in any order and the result is the same up to rounding. What changes is the address sequence the innermost loop produces. The textbook order is i, j, k: one dot product per output cell. This version is used only for the measurements below; it is not in engine.js:

Its inner loop reads A[i*K + k] with stride 1, fine, and B[k*N + j] with stride N floats, 4N bytes. Once 4N ≥ 64, that is once N ≥ 16, every iteration of k lands on a different cache line and uses one float out of the sixteen it fetched. jsMatmul swaps the two inner loops to i, k, j. Its inner loop holds A[i,k] in a local and sweeps j, so both B[kN + j] and out[iN + j] advance by one float:

Counting cache-line loads for a 256 × 256 GEMM

Take M = K = N = 256. Each matrix is 256 KiB, five times the L1. Count line fetches into L1 under two facts about this L1:

  • A row of A or C is 1 KiB, 16 lines. It is reused across a whole inner sweep and stays resident.
  • A column of B is 256 floats, one per row, 1 024 bytes apart. With 64 sets and 64-byte lines, an address’s set is (address / 64) mod 64, so a 1 024-byte stride advances the set by 16 and the column lands in only 4 sets: 4 × 12 = 48 lines of capacity for 256 lines. The column is evicted before the next j could reuse it. Likewise all of B (4 096 lines) cannot survive from one i to the next.

In i, j, k order, every one of the M·N·K reads of B misses. A and C add one line per 16 floats of their rows:

Lijk≈MNK⏟B+MK16⏟A+MN16⏟C=16 777 216+4 096+4 096=16 785 408

In i, k, j order, B is streamed in whole lines, so each of the M·K row sweeps costs N/16 lines:

Likj≈MKN16⏟B+MK16⏟A+MN16⏟C=1 048 576+4 096+4 096=1 056 768

That is 16 785 408 × 64 B ≈ 1.07 GB moved into L1 against 1 056 768 × 64 B ≈ 67.6 MB, a ratio of 15.9: almost exactly the 16 floats per line that the strided order throws away. The model counts L1 fills and ignores hardware prefetchers, which detect constant strides and hide part of the latency.

Where those fills come from decides how much they cost. Measured on the Ryzen 9 9955HX, Node 24.21, one warm run each:

nsize of Bi,j,ki,k,j (jsMatmul)ratio

At n = 256 all of B fits in the 1 MiB L2 per core, so the 16 million extra L1 misses are L2 hits, a few nanoseconds each, and much of that is overlapped. At n = 1 024 B no longer fits in L2 and the strided misses go to L3 and DRAM. The ratio of fills is fixed by the loop order; the ratio of times depends on which level of the hierarchy serves them. Note that the i, j, k listing keeps its running sum in a local, which favours it; the gap is not caused by memory writes.

jsMatmul, line by line

This is the complete function from engine.js, in five consecutive listings with nothing omitted. A test in tests/nn-chapters-links.test.js fails if they stop matching the source.

out defaults to a fresh zero-filled array, but callers may pass one in to avoid allocating per call; the training loops in engine.js do. Line 2 zeroes it either way, because line 10 accumulates with +=: a reused buffer would otherwise add this product to the previous one. Nothing checks that A has M·K elements. A short array gives undefined on an out-of-range read, undefined * x is NaN, and the NaN is stored silently.

The row offsets i·K and i·N are computed once per row instead of once per element. An optimising compiler would usually hoist these itself; writing them out keeps the inner loop to one add per address.

The middle loop walks k, and line 7 reads A[i,k] into the local a. That is the only read of A in the whole multiply, one per (i, k) pair: M·K reads of A in total instead of M·N·K. kN is the start of row k of B.

The hot loop. Per iteration: load out[iN + j], load B[kN + j], one multiply, one add, store out[iN + j]. Both indices step by 1, which is the whole cache argument above. It runs M·K·N times, 16 777 216 for n = 256. The read-modify-write of out is the price of this order: C’s row is reloaded and rewritten K times, but it stays in L1 while that happens.

The function returns the same array it wrote, so jsMatmul(A, B, M, K, N, buf) can be used as an expression without a second allocation.

Float32 storage, float64 arithmetic

Float32Array stores IEEE 754 binary32: 24 significant bits. Every JavaScript number is IEEE 754 binary64: 53 significant bits. JavaScript has no float32 arithmetic. Line 10 therefore runs as follows:

  1. Read out[iN + j] and B[kN + j]: binary32 → binary64. Exact; every binary32 value is a binary64 value.
  2. a * B[kN + j]: the exact product of two 24-bit significands has at most 48 bits, which fits in 53. Exact.
  3. +: rounded once, to binary64.
  4. Store into out: rounded again, to binary32 (round to nearest, ties to even).

The second rounding happens on every one of the K additions into each output, because out is the accumulator. Math.fround(x) performs exactly that store-time rounding, so it can reproduce the effect without a typed array. Sum the binary32 value of 0.1 one million times:

The binary32 sum is 0.96% too high. The reason is spacing. A binary32 number between 215 and 217 has neighbours 2−8 or 2−7 apart, so adding 0.1 there must land on a multiple of that step. Measured: from 32 768 onward each add contributes 0.1015625 instead of 0.1. The sum passes 32 768 after 328 588 additions; the remaining 671 412 each overshoot by 0.0015625, about 1 049 in total, close to the 958 observed (the step below 32 768 undershoots slightly). The error is not random noise; it is a bias set by the accumulator’s magnitude.

In a GEMM the same thing happens in each of the M·N outputs over K terms. Two consequences follow. First, a binary64 local accumulator, as in the i, j, k listing, rounds once at the end instead of K times; the i, k, j order cannot do that because each output is touched in K separate sweeps. Second, other backends round differently: the WebAssembly kernel rounds every product to binary32 before adding it. Over 2 000 random 16-term dot products with entries in (−1, 1), the two disagree in 1 150, each time by one unit in the last place. The WebAssembly chapter shows the instruction responsible.

What the JIT needs: one element kind per access site

V8, the engine in Chrome and Node, does not compile jsMatmul before its first call. It starts by interpreting it and records, at each property or element access in the source, which kinds of object have appeared there. That record is an inline cache. When the function is hot, an optimising compiler uses the recorded feedback to emit machine code specialised for what was seen, guarded by a cheap check that deoptimises back to the interpreter if a new kind turns up.

An access site that has seen one kind is monomorphic. For B[kN + j] with B always a Float32Array, the specialised code is: check B’s map once, check the index against B’s length, load 4 bytes, widen to a double. A site that has seen several kinds is polymorphic, and the compiled code must first branch on which kind it has, then use the matching load. Identical inputs on the timed calls, about 1.5 times slower, because the feedback from the Array calls is permanent for that function. Keep hot numeric code fed with one typed-array type. Engine code that sometimes receives a plain Array should convert it once at the boundary with Float32Array.from.

Bounds checks

A typed-array read past its length returns undefined, and a write past it is ignored. The language requires that, so compiled code must compare every index with the length before touching memory, unless the compiler can prove the comparison always passes. For for (let j = 0; j < arr.length; j++) s += arr[j] the loop condition is that proof, and range analysis can remove the per-iteration check. In jsMatmul the index is iN + j and the loop bound is the parameter N; nothing in the function ties N to out.length, so there is no proof available and the check stays. It costs a compare and a branch that never fails, so the branch predictor gets it right every time; it is small next to the loads it guards. Whether a particular V8 version removes a particular check can only be confirmed by reading its optimised code (Node’s --print-opt-code); this page does not claim more than the mechanism.

The main-thread budget and Web Workers

JavaScript on the main thread shares it with input handling, style, layout and paint. At 60 frames per second a frame is 16.7 ms, and every millisecond of script comes out of it. The n = 256 run above took 23.1 ms in a warm process, 1.38 ns per multiply-add for n³ multiply-adds. Setting the whole frame aside for the multiply gives an upper bound:

n3·1.38 ns≤16.7 ms⇒n≤1.21×1073≈229

With a more realistic 10 ms for script the bound is n ≈ 193. Phones are several times slower per core, so the same arithmetic gives a much smaller n there. Measure on the target device.

Past that, the multiply belongs on another thread. A Web Worker runs its own event loop and its own JavaScript heap. Messages between threads are copied by structured clone, unless the sender lists an ArrayBuffer in the transfer list: then ownership moves, the receiver gets the same memory without a copy, and the sender’s buffer is detached (length 0). This pattern is illustrative; this page does not run it.

Three details matter. Transfer moves the whole buffer, so A and B must each own their buffer exactly: a subarray view would ship its parent, and listing the same buffer twice throws a DataCloneError. Callers that still need the inputs must pass copies (A.slice()). The result travels back the same way, so neither direction copies M·N floats. And the worker only moves the cost off the main thread; for parallel speed-up the work has to be split across several workers, or across WebAssembly threads with shared memory.

The workbench backend comparison runs larger repeatable shapes. Do not rank runtimes from one shape or a single cold run.
